# 从模糊想法到完整项目：Claude Code 使用手册

> 假设你只有一个想法：**"我想做一个系统，能根据任务自动选最合适的 LLM"**
> 以下模拟你和 Claude Code 从头到尾的真实对话流程。

---

## 阶段 0：把模糊想法变清晰

### 你的第一个 prompt（就是你脑子里的原始想法）

```
我有个想法：现在 LLM 越来越多（GPT-4o, DeepSeek, Gemini, Claude...），
不同任务用不同模型效果差很多，价格也差很多。

我想做一个智能路由系统，输入一个任务描述，自动帮我选最合适的模型。

你觉得这个方向可行吗？帮我理一下：
1. 核心要解决什么问题
2. 最小可用版本应该包含什么
3. 有哪些技术难点需要我提前想清楚
```

> **为什么这样问**：你不需要自己想清楚所有细节。把原始想法抛出去，
> 让 Claude 帮你结构化。关键是问"最小可用版本"，防止 scope 膨胀。

### Claude 回答后，你追问

```
你提到了几个技术难点，我想聚焦讨论：

1. "任务分析"这步——是用规则匹配还是让 LLM 自己分析？各有什么优缺点？
2. "模型选择"——除了能力匹配，还需要考虑成本和模型健康度吗？
   我倾向 MVP 先只做能力+成本，健康度后面再加，你觉得呢？
3. 存储——我需要持久化什么数据？SQLite 够用吗？

帮我做个取舍决策表。
```

> **为什么追问**：Claude 第一轮回答通常偏全面，你需要主动砍 scope。
> "我倾向 X，你觉得呢？" 这种问法比 "你帮我决定" 更高效。

> **概念：MVP（Minimum Viable Product，最小可行产品）**
> 用最少的功能构建一个可运行的版本，快速验证核心假设、收集反馈，再迭代改进。
> 三个关键词：**Minimum**（只做最核心功能）、**Viable**（能实际使用）、**Product**（可交付）。
> 以本项目为例，MVP = 任务分析 → 模型注册 → 打分选择 → CLI，不含监控、降级、在线学习。

### 确认 MVP 范围后

```
OK，MVP 就这样定：
- 输入：任务描述（字符串）
- 输出：推荐模型 + 理由 + 分数
- 流程：任务分析 → 候选过滤 → 打分排序 → 返回结果
- CLI 先行，不做 API
- 不做：监控、降级试验、在线学习

帮我写成 PRD 文档，放到 docs/PRD.md。
要求简洁，每个功能点有验收标准。
```

## 阶段 1：架构设计

### 你的 prompt

```
PRD 定了。现在帮我设计架构。

我的初步想法是分成这几块：
- 任务分析器：接收任务描述，输出任务类型和复杂度
- 模型注册表：存储各模型的能力和价格信息
- 路由引擎：根据分析结果和模型信息做匹配打分
- 主程序：串联以上三块，提供 CLI

但我不确定：
1. 这样分是否合理？有没有更好的拆法？
2. 模块之间传什么数据？用什么数据结构？
3. 依赖方向应该怎么设计？

帮我进 Plan Mode 讨论一下。
```

> **为什么先说"我的初步想法"**：给 Claude 一个起点比完全开放式提问效率高很多。
> 即使你的想法不完美，Claude 会在你的基础上优化，而不是从零开始。

### Plan Mode 里的互动

Claude 会给出架构方案。你可能会问：

```
关于数据结构，我有个纠结：
- 用 dataclass(frozen=True) 还是 Pydantic BaseModel？
- frozen dataclass 更轻量但没有验证
- Pydantic 有验证但可能过重

我的场景是内部模块间传数据，不是处理外部输入。你建议哪个？
```

```
模块间的接口，你用的是具体类。
我觉得应该用 Protocol（鸭子类型），这样测试时好 mock。
帮我改成 Protocol 接口。
```

### 确认架构后

```
架构 OK。现在帮我：
1. 创建目录结构（只有空文件，不写实现）
2. 定义共享的数据类型
3. 每个模块写一个 Protocol 接口
4. 初始化 pyproject.toml（用 uv，加上 pytest/ruff/mypy）
5. 写 .env.example 和 .gitignore
6. 每步分开 commit

不要写任何业务逻辑，只搭骨架。
```

## 阶段 2：逐模块 TDD 实现

### 你的通用模板（每个模块开头都用这个）

```
现在实现 [模块名]。用 TDD 方式，先写测试再写实现。

这个模块的职责是 [一句话描述]。

请先帮我想清楚需要测哪些场景，列给我看。
不要直接写代码，先列测试用例让我确认。
```

> **为什么先列用例不写代码**：这一步是你参与设计的关键时刻。
> 测试用例 = 需求规格。你确认了测试用例，就等于确认了这个模块的行为。

### 以 model_registry 为例

```
现在实现 model_registry。用 TDD，先写测试再写实现。

这个模块负责管理 LLM 模型的元数据（名称、provider、能力评分、价格）。

先列测试场景给我看，不写代码。
```

Claude 列出测试场景后：

```
测试场景 OK，补充一个：
- 当两个 provider 都有同名模型时，应该怎么处理？
  （比如 litellm 的 model_id 格式是 "provider/model_name"）

现在写测试代码，放到 route_agent/model_registry/tests/test_registry.py
写完 commit，然后运行 pytest 确认全部 FAIL。
```

确认测试全红后：

```
好的，所有测试都 FAIL 了。
现在写最小实现让它们全部通过。
不要过度设计，能让测试绿就行。
写完运行 pytest + coverage，然后 commit。
```

### 对每个模块重复这个循环

**task_analyzer:**
```
实现 task_analyzer。TDD。
这个模块调用 LLM 分析任务类型和复杂度。

关键约束：
- 测试中不能真的调 LLM API，需要 mock
- LLM 调用失败时必须有 fallback，不能崩溃

先列测试场景。
```

**router_engine/scorer:**
```
实现路由引擎的打分逻辑。TDD。

这是最核心的部分——根据任务分析结果和模型能力做匹配打分。

我想先讨论一下打分算法的设计思路：
- 能力匹配分怎么算？
- 成本分怎么归一化？
- 两者怎么融合？

帮我分析几种方案的优缺点，我来选。
```

> **关键点**：对于核心算法（打分、选择），不要直接让 Claude 实现。
> 先讨论方案，你来做决策。这样你才真正理解自己的系统。

**router_engine/selector:**
```
实现候选选择逻辑。TDD。

在打分之后，我需要从候选中选出最终推荐。

我有几个问题想先讨论：
1. 直接选最高分的行不行？有什么问题？
2. 如果要加"探索"机制（偶尔选非最优的），怎么设计？
3. 同一个 provider 的模型太多会不会有问题？

先讨论，再列测试，再实现。
```

## 阶段 3：串联和验证

### 你的 prompt

```
各模块都实现了。现在串联起来：
1. 写 app.py 把三个模块串联
2. 写 __main__.py 做 CLI 入口
3. 写一个集成测试验证完整流程

然后我要手动试一下：
python -m route_agent "帮我写一个 Python 爬虫"

看看输出是否合理。
```

手动试完后：

```
试了一下，有几个问题：
1. 输出格式不太友好，只有 model_id，我想看到 provider 和价格
2. 分析 "帮我写爬虫" 这种中文输入时，task_type 是 "general" 而不是 "coding"
3. 所有模型分数差异太小，看不出区分度

帮我逐个排查和修复。每修一个问题，先改测试再改实现。
```

> **为什么每个问题都"先改测试再改实现"**：这样你的测试始终是需求的真实反映，
> 不会出现"实现改了但测试没跟上"的情况。

## Phase 2：加功能（每个功能独立会话）

### 你开始一个新功能时的 prompt 模板

```
接着 Route Agent 项目。

上次 MVP 做完了，包含：任务分析 → 模型注册 → 打分选择 → CLI。

现在我想加 [功能名]。
背景是 [为什么需要这个功能，解决什么问题]。

我的初步想法是 [你的思路，哪怕很粗略]。

帮我进 Plan Mode，先确认方案再实现。
```

> **为什么要说"上次做了什么"**：新会话没有之前的上下文。
> 用 1-2 句话概括现状，Claude 就能快速对齐。
> 如果有 CLAUDE.md 和 ARCHITECTURE.md，Claude 会自动读取，但你显式说一下更准确。

## 发问的核心原则

### 1. 先说你的想法，再问 Claude 的意见
```
❌ "帮我设计打分算法"
✅ "我觉得打分可以用加权平均，但不确定权重怎么定。你觉得呢？"
```

### 2. 每次只推进一步，不要一次性描述整个系统
```
❌ "帮我实现完整的路由系统，包括分析、注册、打分、选择、监控、降级..."
✅ "现在只做 model_registry 这一个模块。TDD，先列测试场景。"
```

### 3. 对核心决策自己拍板，对样板代码让 Claude 自主
```
你来决定的：打分公式、选择策略、数据结构设计、MVP scope
Claude 来做的：测试代码编写、存储层实现、CLI 解析、格式化
```

### 4. 遇到不确定时，要求 Claude 给选项而非直接决定
```
"这里有几种实现方式，帮我列出各自的优缺点，我来选。"
```

### 5. 每步完了就 commit，不积累
```
每个 prompt 结尾加一句："写完跑测试，然后 commit。"
```

### 6. 发现跑偏时立刻拉回来
```
"停。这不在 MVP 范围内。回到 [具体任务]。"
"这太复杂了。我只需要最简单的能工作的版本。"
"先不要优化。能跑就行，优化是下一步。"
```

## 实操技巧集

### 技巧 1：CLAUDE.md 是你的"项目系统提示词"

Claude Code 每次对话开始会**自动读取** `CLAUDE.md`。把它当成你给 Claude 的常驻指令。

**该写什么：**
```markdown
# CLAUDE.md

## 项目概述（让 Claude 秒懂项目）
一句话说清项目做什么

## 运行命令（让 Claude 知道怎么跑测试/构建）
uv run pytest -q
uv run ruff check .

## 架构概览（让 Claude 知道去哪找代码）
- route_agent/scorer.py — 打分逻辑
- route_agent/selector.py — 候选选择

## 给 Claude 的规则（强制行为）
- 改代码必须先改测试
- 不要用 print，用 logging
- commit message 用中文
```

**不该写什么：**
- 过长的历史记录（Claude 每次都会读，浪费 token）
- 临时的 TODO（用 GitHub Issues）
- 通用的编程知识（Claude 已经知道了）

> 你的项目 CLAUDE.md 写得不错，但可以加上 **"给 Claude 的规则"** 这一节，
> 比如强制 TDD 和 logging，这样就不用每次 prompt 里重复说。

---

### 技巧 2：用 /compact 管理上下文窗口

Claude Code 的上下文窗口有限。长对话到后面，Claude 会"忘记"前面的内容。

**什么时候手动 compact：**
```
场景：你完成了模块 A 的实现，准备开始模块 B
你说：/compact
效果：Claude 压缩之前的对话，保留关键信息，释放上下文空间
```

**更好的做法——按任务分会话：**
```
会话 1：实现 model_registry（完成后结束）
会话 2：实现 task_analyzer（完成后结束）
会话 3：实现 router_engine（完成后结束）
```

> 每个模块一个会话，比在一个超长会话里做所有事情更可靠。
> 因为 CLAUDE.md 和代码文件每次都会重新读取，不会丢失上下文。

---

### 技巧 3：让 Claude 自我审查

写完代码后，不要自己 review，让 Claude 换个视角帮你查：

```
代码写完了。现在用 code-reviewer 的视角帮我审查：
1. 有没有安全问题（注入、密钥泄露）
2. 有没有并发问题（竞态、死锁）
3. 有没有性能问题（N+1 查询、不必要的循环）
4. 有没有违反项目规范的地方

只列问题，不要自动修复。
```

或者更直接：
```
假装你是另一个工程师，review 我刚才写的代码。要严格。
```

---

### 技巧 4：用具体的反例约束输出

Claude 容易过度设计。用"不要"比"要"更有效：

```
❌ "帮我写一个简单的打分函数"
   → Claude 可能还是会写 200 行

✅ "帮我写一个打分函数。约束：
   - 不超过 30 行
   - 不要用类，用纯函数
   - 不要加缓存/memoization
   - 不要处理边界情况，我后面单独加"
   → Claude 会严格遵守
```

```
❌ "帮我重构这个模块"
   → Claude 可能重写整个文件

✅ "只重构 compute_score 函数。
   不要动其他函数。
   不要改接口签名。
   不要加新的依赖。"
```

---

### 技巧 5：用"先读后改"的节奏

永远不要直接说"改 scorer.py 的逻辑"。先让 Claude 读懂现状：

```
第一步：
"读一下 route_agent/router_engine/scorer.py，
 告诉我 compute_dimension_score 的逻辑是什么。"

第二步（确认 Claude 理解正确后）：
"理解得对。现在改一下：当维度缺失时，用 0.5 而不是中位数。"
```

> 为什么：如果 Claude 理解错了现有逻辑，直接改会改出 bug。
> 先确认理解，再动手，省下的是 debug 时间。

---

### 技巧 6：用 TodoWrite 当"进度条"

复杂任务拆成 TODO 列表，Claude 会逐个完成并标记：

```
帮我做以下 5 件事（用 TodoWrite 跟踪进度）：
1. 给 scorer.py 加 compute_overload_penalty 函数
2. 在 selector.py 中调用这个函数
3. 写单元测试
4. 跑全量测试确认没有 regression
5. commit
```

> 好处：你可以实时看到进度，Claude 也不会漏步骤。

---

### 技巧 7：利用并行 Agent 加速

当多个任务互不依赖时，可以让 Claude 并行处理：

```
帮我并行做这三件事：
1. Agent 1：review scorer.py 的安全性
2. Agent 2：review selector.py 的性能
3. Agent 3：检查所有 TODO/FIXME 注释

三个结果汇总后告诉我。
```

> Claude Code 支持同时启动多个 sub-agent，比串行快 3x。

---

### 技巧 8：用 "假如" 探索设计空间

在做决策前，用假设性问题探索不同方向：

```
假如我们要支持 100 个并发请求，scorer.py 里的哪些部分会成为瓶颈？

假如我不用 SQLite 而用纯内存存储，代码需要改什么？改动量大吗？

假如以后要加 REST API，现在的架构需要提前做什么准备？
```

> 这比直接问"怎么设计"更聚焦，Claude 的回答也更有针对性。

### 技巧 9：善用 "恢复会话" 和 记忆文件

**跨会话的上下文传递：**

方式 1 — `/resume` 命令恢复上次会话
```
/resume
（自动加载上次的会话日志，Claude 知道你上次做了什么）
```

方式 2 — 在 `~/.claude/projects/<项目>/memory/MEMORY.md` 写笔记
```
Claude 每次会话开始会自动读取这个文件。
用它记录：项目的长期决策、反复出现的 bug、你的偏好设定。
```

方式 3 — 让 Claude 记住
```
"帮我记住：这个项目里 print() 是被禁止的，永远用 logging。"
→ Claude 会写入 memory 文件，下次自动生效。
```

### 技巧 10：Debug 时给 Claude 完整的错误上下文

```
❌ "测试挂了，帮我修"
   → Claude 不知道什么测试、什么错误

✅ "运行 uv run pytest route_agent/router_engine/tests/test_scorer.py

```
> Claude 会自己执行、自己看 traceback、自己修。

## Route Agent 项目复盘：哪些步骤可以改进

| 实际做的 | 更好的做法 |
|-----------|-----------|
| 一开始就包含 monitoring + downgrade + config.yaml | 第一个 prompt 就明确 MVP 只做核心三模块 |
| 55e479c 一个 commit 包含全部模块 | 每个模块单独 TDD 循环，单独 commit |
| 先写了性能测试（434 行），核心模块无单元测试 | 先问 Claude "列出测试场景"，确认后再写测试和实现 |
| escalation/scorer/selector 改了代码没写测试 | 每次改代码前说"先改测试再改实现" |
| FastAPI 在依赖中但没使用 | 第一个 prompt 就说"CLI 先行，不做 API" |
| 边开发边写面试题库 | 开发完后单独一个会话整理知识 |
