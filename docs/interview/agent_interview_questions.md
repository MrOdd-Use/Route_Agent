# AI Agent / RAG 面试问题整理

> 适用方向：AI Agent、RAG、智能排障、企业级 Agent 平台、Agent 产品设计  
> 使用方式：优先回答“结论 + 方法 + 工程化兜底”，少讲空话，多讲机制、边界和取舍。


## 一、故障判断与 AI 排障

### 1. 如果系统出现异常，怎么判断是网络抖动还是系统真实故障？


**标准回答**

如果系统出现异常，我不会因为一次失败就直接定义成系统故障，而是会先做分层判断，把网络链路问题和服务本身故障区分开。

第一，看错误特征。网络抖动通常表现为超时、连接重置、延迟瞬时升高、短暂 5xx，这类现象往往是瞬时、局部、可恢复的；真实故障通常更持续，比如接口持续报错、健康检查持续失败、业务逻辑稳定异常。

第二，看时间窗口和重试结果。单次失败不下结论，而是在短时间窗口内做有限次重试，并配合指数退避。如果重试后快速恢复，更像网络抖动；如果连续失败且模式一致，更像系统故障。

第三，看多点观测。如果只有单节点、单链路、单可用区异常，而其他探测点正常，大概率是网络侧问题；如果多个节点、多个调用路径同时异常，更可能是服务真实故障。

第四，看调用侧和服务侧指标是否一致。如果调用方报超时，但服务端 CPU、内存、线程池、错误率、健康检查都正常，就优先怀疑链路；如果服务端本身也有资源打满或错误日志激增，那就不是单纯抖动。

第五，机制上避免误判。一般会结合阈值判断、主动探测、重试与熔断、疑似网络问题标签这些机制，避免把短暂抖动误判成真实故障。

**一句话版**

我的原则是单点瞬时失败不直接定义为系统故障，而是结合错误类型、持续时间、重试结果、多点观测和服务端健康状态做综合判断。

**面试官关注点**

- 会不会因为单次失败就误判
- 是否理解时间窗口、重试、阈值、多点观测
- 是否知道调用侧和服务侧要联合判断
- 是否有工程化兜底而不是拍脑袋

### 2. 如果 AI Agent 给出的排障建议和实际不符，怎么处理？


**标准回答**

如果 AI Agent 的排障建议与实际不符，我会把它当成高风险决策偏差，而不是一次普通回答错误。核心思路是，不让模型的单次判断直接变成生产动作，而是通过证据校验、规则约束和人工确认把风险兜住。

第一，模型只负责建议，不直接执行高风险动作。像重启核心服务、切流、删数据、改配置这类操作，必须放在审批或规则系统后面。

第二，要求结论必须带证据。比如它判断是数据库连接池耗尽，就必须同时给出连接数、慢查询、连接获取失败日志、依赖链超时等支撑信息。没有证据的只能叫假设，不能叫结论。

第三，做多路交叉校验。Agent 的判断要和监控、日志、链路追踪、健康检查做比对。如果模型结论和真实观测冲突，优先相信可观测数据。

第四，做风险分级。低风险建议可以自动推进，只读检查和补充信息可以自动执行；中风险动作要求确认；高风险动作必须人工审批。

第五，做错误闭环。发现建议不符后，要回溯是上下文缺失、检索错误、推理偏差还是表达过度确定，再分别优化检索、提示词、规则校验器和评测集。

**一句话版**

处理大模型幻觉的关键不是假设模型永远正确，而是把系统设计成即使模型判断错了，也不会直接造成错误执行。

## 二、RAG 检索、召回与算法

### 3. RAG 检索准确率怎么统计？


**标准回答**

RAG 检索准确率不能只看一个笼统的 accuracy，一般要拆成召回、排序和端到端效果三层来评估。

离线评估通常先准备一批标注集，每条样本包含用户问题、标准证据、相关文档或 chunk 标注。基于这批数据，常见指标有：

- `Recall@K`：前 K 条结果里有没有把正确证据召回出来，主要看漏不漏。
- `Precision@K`：前 K 条结果中相关结果占比，主要看噪音多不多。
- `Hit Rate@K`：前 K 条里是否至少命中一条正确结果。
- `MRR`：看第一个正确结果排得靠不靠前。
- `nDCG`：适合多个相关结果且相关性有等级差异的场景。

线上不只看检索层，还要看是否真正帮助最终回答。常见指标包括最终答案正确率、追问率、满意度、人工改写率、有证据支撑的回答占比。

实际项目里，通常会重点看 `top3/top5` 的召回，因为大模型实际消费的就是前几个 chunk。另外最好做到 chunk 级评估，而不只是文档级评估，因为送给模型的是 chunk，不是整篇文档。

**一句话版**

RAG 检索评估本质上不是一个单指标，而是用 `Recall@K` 看有没有找到，用 `Precision@K` 看噪音多少，用 `MRR/nDCG` 看排序质量，再结合最终答案效果做端到端评估。

#### 补充：MRR 是什么？

`MRR` 是 `Mean Reciprocal Rank`，中文一般叫平均倒数排名。

它主要衡量的是：对于一批查询，系统把第一个正确结果排得有多靠前。

计算方式是：

- 先看每个问题中，第一个正确结果排在第几位
- 再取这个排名的倒数
- 最后对所有问题求平均

例如：

- 问题 A，第一个正确结果排第 1，得分是 `1/1 = 1`
- 问题 B，第一个正确结果排第 2，得分是 `1/2 = 0.5`
- 问题 C，第一个正确结果排第 5，得分是 `1/5 = 0.2`

那么这三条样本的 `MRR = (1 + 0.5 + 0.2) / 3 = 0.5667`。

如果某个问题完全没有命中正确结果，通常记为 `0`。

在 RAG 里，`MRR` 主要看排序质量。因为很多时候问题不是“没召回到”，而是“召回到了但排得太后”，模型在有限上下文里根本用不上。

**面试表达**

MRR 是平均倒数排名，用来评估检索或排序系统中，第一个正确结果排得是否靠前。它越高，说明系统越能把正确结果放在前面，适合衡量 RAG 检索阶段的排序效果。

### 4. 召回率和准确率怎么区分？


**标准回答**

召回率看的是“该找出来的内容，你找出来了多少”；准确率更准确地说是精确率，看的是“你找出来的内容里，有多少是真的相关”。

公式上：

- 召回率 = 检索出的相关结果数 / 系统中所有相关结果数
- 精确率 = 检索出的相关结果数 / 检索出的结果总数

如果知识库里一共有 8 条真正相关的文档，系统返回了 10 条，其中 6 条相关、4 条无关，那么召回率是 `6/8 = 75%`，精确率是 `6/10 = 60%`。

在 RAG 里，召回率低意味着正确知识没被捞上来；精确率低意味着喂给模型的噪音太多。工程上通常是召回阶段优先保证召回率，重排阶段再提升精确率，也就是先高召回，再高精排。

**一句话版**

召回率关注漏没漏，精确率关注准不准；RAG 里两者都重要，但通常先保召回，再用 rerank 提精度。

#### 补充：RAG 还有哪些评价指标？

RAG 的评价不能只看检索阶段，完整的评估体系一般要覆盖检索、生成和端到端三层，再配合专用评测框架做系统化度量。

**检索阶段指标**

前面已经提到 `Recall@K`、`Precision@K`、`MRR`、`nDCG`、`Hit Rate@K`，这些主要衡量"有没有找到"和"排得好不好"。

**生成阶段指标**

- `Faithfulness`（忠实度）：生成内容是否基于检索到的上下文，有没有脱离证据乱编。
- `Answer Relevancy`（答案相关性）：生成的答案和用户问题的语义相关程度，有没有答偏。
- `Answer Correctness`（答案正确性）：和 ground truth 对比，答案的事实准确度。

**端到端指标**

- `Context Relevancy`：检索出的上下文和问题的相关程度，衡量检索结果对生成的支撑力。
- `Context Utilization`：生成答案时实际使用了多少检索内容，是否存在"召回了但没用上"。
- `Noise Robustness`：混入无关文档后，答案质量的衰减程度。
- `Latency`：检索加生成的端到端响应时间。

**RAGAS 评测框架**

`RAGAS` 是目前最主流的 RAG 专用评测框架，核心指标有四个：

1. `Faithfulness`：答案中的每个声明是否都能在 context 中找到依据。
2. `Answer Relevancy`：答案与问题的语义相关性。
3. `Context Precision`：相关 context 是否排在前面，而不是被噪音淹没。
4. `Context Recall`：ground truth 中的信息是否被 context 覆盖。

RAGAS 的思路是把 RAG 的评估拆成检索质量和生成质量两个独立维度，分别打分后再综合分析，避免端到端指标掩盖具体环节的问题。

**其他进阶指标**

- `Hallucination Rate`：生成内容中无法溯源到检索文档的比例。
- `Chunk Attribution`：每段生成内容能否指向具体的 chunk 来源，衡量可追溯性。
- `Robustness to Paraphrase`：同一问题换种说法，答案的一致性。
- `Counterfactual Robustness`：检索到矛盾信息时，模型是否能正确处理而不是盲目采信。
- `Information Integration`：需要综合多个 chunk 才能回答时的表现。

**面试表达**

RAG 评估不能只看检索阶段的 Recall 和 Precision。完整体系要覆盖三层：检索层用 `Recall@K`、`MRR` 衡量召回和排序质量；生成层用 `Faithfulness` 看有没有编、`Answer Relevancy` 看有没有答偏；端到端用 `Context Relevancy`、`Noise Robustness`、`Latency` 看整体效果。目前主流的专用框架是 RAGAS，把检索质量和生成质量拆开独立评估，避免端到端指标掩盖具体环节的短板。实际项目里通常组合使用：检索用 Recall@K + MRR，生成用 Faithfulness + Answer Relevancy，再加端到端延迟作为工程指标。

### 5. RAG 知识库系统怎么做全链路设计？


**标准回答**

如果让我设计一个 RAG 知识库系统，我一般按六层来看：数据接入层、数据处理层、索引构建层、检索召回层、生成编排层、评估运营层。

第一，数据接入层。负责接入 PDF、Word、Wiki、FAQ、业务系统数据和外部资料，同时处理多源同步、增量更新、版本管理和权限继承。

第二，数据处理层。负责文档解析、清洗、去噪、切块和元数据补充。切块一般优先采用结构化切块加适度 overlap，保留标题、章节路径、更新时间、业务域、权限标签等信息。

第三，索引构建层。通常同时建设向量索引和关键词倒排索引，支持混合检索，并考虑索引增量更新、失效删除、多租户隔离和模型升级后的重建策略。

第四，检索召回层。先做 query 理解和改写，再做多路召回，比如向量召回、BM25、FAQ 精准命中、metadata 过滤召回，之后做融合和 rerank，最后筛出最适合进入上下文的证据。

第五，生成编排层。把用户问题、检索证据、系统指令和回答格式要求组装成 prompt，要求模型基于证据回答，并支持引用、校验、敏感信息过滤、拒答和降级。

第六，评估运营层。离线看 `Recall@K`、`Precision@K`、`MRR`、答案正确率、幻觉率；在线看满意度、追问率、转人工率、时延和热门问题覆盖率，并把失败 case 回流优化。

在企业场景里，还要特别注意权限控制、新鲜度管理、缓存与性能、失败兜底和全链路可观测性。

**一句话版**

完整 RAG 系统不是“文档切块 + 向量库 + 大模型”这么简单，而是从知识接入、处理、索引、检索、生成到评估闭环的一整条工程链路。

#### 补充：Prompt、RAG、精调 / 微调怎么选？

这三者解决的问题并不一样，核心区别在于：Prompt 主要是临时约束模型行为，RAG 主要是给模型补外部知识，精调 / 微调主要是把任务模式和输出习惯训练进模型。

| 方式 | 主要解决什么问题 | 知识或能力放哪 | 优点 | 局限 | 更适合的场景 |
|---|---|---|---|---|---|
| Prompt | 临时告诉模型“这次该怎么做” | 直接写在 prompt 里 | 上手最快、成本最低、实验灵活 | 稳定性一般，复杂任务容易漂移 | 原型验证、轻量格式约束、简单问答 |
| RAG | 让模型拿到外部最新知识再回答 | 文档库、向量库、FAQ、数据库等模型外部系统 | 知识更新快、可引用依据、不需要重新训练 | 依赖检索质量，工程链路更复杂 | 企业知识库问答、客服、制度查询、文档助手 |
| 精调 / 微调 | 让模型更稳定地按指定方式做事 | 写进模型参数 | 风格更稳、格式更稳、领域任务适配更强 | 更新成本更高，不适合频繁变化的事实知识 | 分类、抽取、固定格式生成、品牌语气、垂直任务适配 |

如果换成一句更工程化的话来说：

- `Prompt` 解决的是“这次怎么说、怎么做”
- `RAG` 解决的是“模型现在该知道什么”
- `精调 / 微调` 解决的是“模型以后更擅长按什么方式做事”

实际项目里它们通常不是互斥关系，而是组合使用：

- 知识经常变化、还要求可引用：优先 `RAG`
- 输出格式和行为习惯要求很强：优先 `精调 / 微调`
- 需求还在探索期，先快速验证：优先 `Prompt`
- 既要最新知识，又要稳定格式：常见做法是 `RAG + Prompt`，必要时再叠加 `精调`

例如：

- “公司 2026 年报销制度是什么？”更适合 `RAG`，因为制度会变，重点是拿到最新文档并基于证据回答。
- “把客服回复统一成品牌语气，并严格输出 JSON”更适合 `精调 / 微调`，因为重点是风格一致性和格式稳定性。
- “先快速验证一个合同字段抽取 Demo”通常先用 `Prompt`，如果效果不稳定，再考虑 `精调 / 微调`。

**面试表达**

Prompt、RAG 和微调的关注点不一样。Prompt 更像临时指令控制，适合快速试错；RAG 用来补充模型外部知识，适合知识经常变化、还要求可追溯的场景；微调则是把特定任务模式、输出格式和行为偏好训练进模型，适合稳定高频的垂直任务。工程上通常不是三选一，而是按“知识更新频率、行为稳定性要求、成本和时效”做组合设计。

### 6. RAG 检索模块召回错误结果时，怎么处理？


**标准回答**

如果 RAG 召回了错误结果，我会先判断问题出在哪一层：是 query 理解错了、召回策略有问题、排序不准，还是 chunk 本身切坏了。

处理上通常分四步。

第一，先识别召回质量。看相关度分数是否过低、不同召回通道是否冲突、是否命中了关键实体和约束。如果整体质量差，不直接进入生成。

第二，优先修 query。很多错召回不是索引坏了，而是用户问题太口语、太模糊或者上下文缺失，所以会做 query rewrite、实体补全、同义词归一化、缩写展开和错别字纠正。

第三，用混合检索和 rerank 修正。向量召回负责语义，BM25 负责关键词，FAQ 或规则负责高频精准命中，然后再用 rerank 把噪音压下去。

比如在电商客服场景里，用户问“买错了怎么退货”，向量召回可以找出“下单后不想要了如何申请退款”这类语义相近内容，BM25 可以命中“退货”“买错了”这些关键词，FAQ 或规则则可以直接命中预先配置好的高频标准问答，比如“买错了怎么退货 -> 可在订单页申请 7 天无理由退货”。最后再用 rerank 把“退货运费谁承担”这类虽然相关但不是当前主问题的结果压下去。

第四，控制进入 prompt 的上下文。限制 topN、设置最低相关度阈值、去重、冲突检测。若证据仍然不足，就拒答、返回文档列表或者转人工，而不是强行生成。

最后要把错召回 case 沉淀成评测集，持续优化切块、索引、召回策略和重排模型。

**一句话版**

错召回不可怕，可怕的是系统没有识别、修正和兜底能力。

### 7. BM25 / 倒排召回怎么实现？


**标准回答**

BM25 / 倒排召回本质上是关键词精确检索，特别适合错误码、接口名、参数名、版本号、类名、表名这类精确词匹配场景。

先说倒排索引。倒排索引可以理解成把“文档里有哪些词”反过来存成“每个词出现在哪些文档或 chunk 里”。例如有三段内容：

- `chunk1`：数据库连接池耗尽导致请求超时
- `chunk2`：网络抖动会引起连接重置
- `chunk3`：连接池参数 `maxActive` 配置过小

做成倒排索引后，大概会变成：

- 数据库 -> `chunk1`
- 连接池 -> `chunk1`、`chunk3`
- 超时 -> `chunk1`
- 网络抖动 -> `chunk2`
- 连接重置 -> `chunk2`
- `maxActive` -> `chunk3`

这样用户搜“连接池 超时”时，系统就能先快速定位包含这些词的候选 chunk。

倒排索引通常和 BM25 配合使用。可以把它理解成两步：

1. 倒排索引先负责召回，也就是根据 query 中的关键词，把可能相关的文档或 chunk 快速找出来。
2. BM25 再负责打分排序，也就是对这些候选结果计算相关性分数，决定谁排在前面。

所以倒排索引解决的是“怎么快速找到”，BM25 解决的是“找到之后谁更相关”。

实现上，先把文档按段落或语义切成 chunk，对正文建立倒排索引。工程上一般会用 Elasticsearch、OpenSearch、Lucene，而不是自己手写搜索引擎。

查询时，对用户问题做同样的预处理，比如分词、大小写归一化、停用词处理、同义词扩展和专有名词保护，然后用 BM25 给每个 chunk 算相关性分数。

BM25 的核心考虑四件事：

- 词有没有出现
- 词频有多高
- 这个词在全库里是不是稀有词，也就是 IDF
- 文档长度归一化，避免长文天然占便宜

例如用户搜索“连接池 超时”时，倒排索引会先找到包含这些词的 `chunk1` 和 `chunk3`，再由 BM25 结合词频、IDF 和长度归一化判断 `chunk1` 更相关，因为它同时命中了“连接池”和“超时”，通常会排在更前面。

在 RAG 里，BM25 通常不单独使用，而是和向量召回一起组成混合检索，再经过 rerank 统一排序。

**一句话版**

BM25 的价值在于对关键词命中很稳，尤其适合向量检索不擅长的错误码、参数名、版本号和专有名词场景。

### 8. BM25 算法的数学原理是什么？它相比简单 TF-IDF 有哪些改进？


**标准回答**

BM25 本质上是一种基于概率检索思想的相关性打分函数，可以理解成“在 TF-IDF 的基础上，进一步把词频增长和文档长度影响做了更合理的建模”。

它的核心打分公式可以写成：

`score(D, Q) = sum(IDF(q_i) * ((tf_i * (k1 + 1)) / (tf_i + k1 * (1 - b + b * |D| / avgdl))))`

这里面几个核心变量可以这样理解：

- `q_i`：query 里的某个词
- `tf_i`：这个词在文档 `D` 中出现的次数
- `IDF(q_i)`：这个词在整个语料库里的区分度，越稀有通常权重越高
- `|D|`：当前文档长度
- `avgdl`：语料库平均文档长度
- `k1`：控制词频饱和速度
- `b`：控制文档长度归一化强度

从直觉上看，BM25 主要做了三件事。

第一，它保留了 TF-IDF 的核心思想，也就是：

- 一个词在当前文档里出现越多，通常越相关
- 一个词在全库里越稀有，区分度越高

第二，它对词频做了饱和处理。简单 TF-IDF 往往会让词频线性增长，也就是一个词出现 10 次和出现 3 次，分数差可能被拉得过大。但实际检索里，一个词出现很多次，不代表相关性会无限增加。BM25 用 `k1` 做了非线性压缩，让词频收益逐步变缓。

第三，它对文档长度做了更合理的归一化。长文档天然更容易命中更多词，如果只用简单 TF-IDF，长文容易占便宜。BM25 用 `b` 和 `|D| / avgdl` 对文档长度做归一化，避免“因为篇幅长所以更容易得高分”。

如果和简单 TF-IDF 对比，我一般会这样总结它的改进点。

第一，TF-IDF 更像一个基础加权方法，BM25 更像一个更接近真实检索行为的打分函数。

第二，TF-IDF 对词频通常是线性或近线性处理，BM25 引入词频饱和，避免高频词把分数拉得过头。

第三，TF-IDF 的文档长度处理通常比较粗，甚至很多简化实现里不做；BM25 显式把文档长度归一化纳入公式。

第四，BM25 在搜索和 RAG 的关键词检索场景里通常更稳，尤其适合错误码、参数名、接口名、版本号这类精确词匹配。

你也可以用一个更面试化的说法：

TF-IDF 解决的是“词的重要性加权”，而 BM25 进一步解决了“词频不能无限涨分”和“长文档不能天然占优”这两个问题，所以它比简单 TF-IDF 更适合实际检索排序。

**一句话版**

BM25 可以理解成 TF-IDF 的工程增强版。它保留了词频和逆文档频率的核心思想，但通过词频饱和和文档长度归一化，让相关性打分更符合真实检索场景，所以在搜索和 RAG 的关键词召回里通常比简单 TF-IDF 更稳。

### 9. 混合检索是怎么做的？


**标准回答**

混合检索的核心思路是把关键词匹配能力和语义理解能力结合起来。BM25 擅长精确词匹配，向量检索擅长语义相似，两者单独用都会有短板。

一个典型流程是：

1. 先做 query 预处理，比如改写、关键词抽取、实体识别和上下文补全。
2. 并行走多路召回，常见是 BM25、向量召回、FAQ 精准匹配、metadata 过滤召回。
3. 对结果做合并去重和分数融合。
4. 用 rerank 模型统一重排。
5. 选 topN 的 chunk 给大模型。

融合时不能简单拼接，因为 BM25 分数和向量相似度不是同一个量纲。常见方法有：

- 归一化后加权融合
- `RRF` 这类基于排名的融合
- 先并集合并，再交给统一 reranker

例如电商客服里，用户问“买错了怎么退货”，系统可以这样走：

- BM25 召回：命中“退货流程说明”“7 天无理由退货规则”这类关键词相关内容。
- 向量召回：找出“下单后不想要了如何申请退款”“商品未使用时怎么申请售后”这类语义相近内容。
- FAQ / 规则召回：直接命中高频标准问答，比如“买错了怎么退货 -> 可在订单页申请 7 天无理由退货”，或者通过“买错 + 退货”规则给该答案强提升。
- rerank 重排：把候选结果重新排序，让“买错商品如何申请退货”排在前面，把“退货运费由谁承担”这类噪音结果压下去。

这样 FAQ 在混合检索里承担的角色就很清楚：它不是泛泛的“常见问题栏目”，而是人工维护的高频标准问答库，用来保证高频问题能被稳定、精准地命中。

实际项目里通常还会根据 query 类型动态调权。比如错误码和参数名类问题，BM25 权重更高；自然语言问答，向量权重更高。

**一句话版**

混合检索的目标不是简单叠加多路召回，而是在不明显增加噪音和时延的前提下，同时兜住精确匹配和语义匹配两类场景。

### 10. Faiss 向量库里的 HNSW 检索怎么理解？


**标准回答**

Faiss 里的 HNSW 是一种基于分层图的近似最近邻检索方法。它不是先把向量分桶，而是把向量组织成多层小世界图，查询时先从高层快速定位，再逐层下探到更细粒度的近邻。

建索引时最关键的参数有：

- `M`：每个节点保留多少邻居，影响图的稠密度、精度和内存
- `efConstruction`：建图时搜索候选邻居的深度，越大建图质量通常越高，但构建更慢

查询时核心参数是：

- `efSearch`：搜索时保留多少候选节点，越大召回率通常越高，但延迟也会上升

它的优点是检索速度快、精度高，适合内存比较充足的场景；缺点是内存占用高、不适合频繁删除、对大量重复向量不够友好。

在 RAG 里，HNSW 一般作为向量召回通道使用，再与 BM25 做混合召回。

**一句话版**

HNSW 可以理解成一张分层导航图，查询时先粗定位，再细搜索，用速度换取近似召回效率。

### 11. RAG 出现漏召时，怎么优化检索模块？


**标准回答**

漏召通常不是单点问题，我会先区分是“根本没召回到”，还是“召回到了但没排上来”。

如果根本没召回到，重点会放在这几类优化：

- 优化 query rewrite、实体补全、同义词归一化
- 优化 chunk 切分，避免切太碎或切太大
- 增加混合检索，不只依赖单一路径
- 调整 topK、ANN 参数、embedding 模型和距离度量方式
- 检查知识接入、索引更新、metadata 和权限过滤是否有问题

如果是召回到了但没排上来，重点优化 rerank 和排序特征，比如标题匹配、关键词命中、新鲜度、权威性和 cross-encoder 重排。

最后要把真实漏召 case 沉淀成评测集，用 `Recall@K`、`HitRate@K`、`MRR` 这些指标持续回归。

**一句话版**

漏召优化不是只调一个参数，而是同时提升“找得到”和“排得上来”的能力。

### 12. rerank 有哪些常见手段？


**标准回答**

RAG 里的 rerank，本质上是对召回阶段拿到的候选结果做第二次更精细的排序。常见做法可以分四层。

第一，规则式 rerank。比如关键词命中、标题命中、错误码精确匹配、时效性、来源权威性加权。优点是简单、可解释、上线快。

第二，基于特征的 Learning to Rank。把 BM25 分数、向量相似度、点击率、新鲜度、来源可信度等特征交给排序模型综合打分。适合已有业务数据积累的场景。

第三，Cross-Encoder rerank。把 query 和候选 chunk 成对输入模型，直接输出相关性分数。这是 RAG 里最常见的高精度 rerank 方式，但成本和时延更高，所以通常只对 topK 候选使用。

第四，LLM rerank。让大模型直接判断候选相关性，适合复杂高价值场景，但成本更高、稳定性和吞吐更差。

实际项目里通常是组合用法，先规则过滤，再特征粗排，最后用 cross-encoder 精排。

**一句话版**

rerank 的核心不是“用哪个模型最先进”，而是精度、延迟、成本之间的平衡。

## 三、Agent Memory 与上下文机制

### 13. Agent memory 管理有哪些难点？


**标准回答**

Agent memory 的难点不只是“上下文太长”，而是记什么、怎么记、什么时候取、什么时候忘、如何保证取出来的是对的。

核心难点通常有：

- 写入策略难。不是所有信息都值得记，记太多会污染，记太少又会失忆。
- 长短期边界不清。很多信息是阶段性有效，不是永远长期，也不是马上失效。
- 检索容易误召。存了正确记忆，不代表用的时候一定取对。
- 一致性难。旧记忆可能和新事实冲突，需要更新、失效和版本控制。
- 摘要压缩容易失真。压缩后可能丢关键条件，甚至产生幻觉。
- 任务状态容易断链。Agent 不仅要记事实，还要记做到哪一步、试过什么、排除了什么。
- 隐私和权限问题复杂。企业场景里要防越权和跨用户污染。
- 评估难。memory 的好坏往往体现在任务完成质量上，不容易靠单一指标衡量。

**一句话版**

memory 管理本质上是一个动态知识管理问题，不是简单把历史对话塞进上下文窗口。

### 14. 多轮对话里的 short-term memory、long-term memory、task memory 怎么做？


**标准回答**

我一般把 Agent memory 分三层。

第一，Short-term memory，也可以理解为 working memory。主要保存最近几轮对话、当前任务变量、最近工具结果和当前计划。实现上通常是保留最近原始上下文，加 rolling summary，再把关键状态抽成结构化字段。

第二，Long-term memory。主要保存用户偏好、稳定事实、长期约束和历史经验。实现上一般会做事件抽取、记忆写入 gating，然后落到向量库、KV 或图数据库里，并带上时间戳、来源和置信度，读取时按 `recency + relevance` 检索。

第三，Task memory。记录的是某个任务过程中的状态，比如任务做到哪一步、哪些假设已经验证过、哪些工具已经调用过、哪些失败过以及下一步是什么。它比 short-term 更结构化，比 long-term 更临时，本质上是任务状态存储。

**一句话版**

Short-term 解决当前连续性，Long-term 解决跨会话持续性，Task memory 解决复杂任务执行过程的状态稳定性。

#### 补充：Long-term memory 一般如何有效实现？

Long-term memory 要想真正有效，关键不是“把更多历史都存下来”，而是要解决四件事：记什么、存在哪里、怎么取、什么时候更新或遗忘。

第一，先做记忆写入筛选，也就是 memory gating。不是所有对话都值得进入长期记忆，通常只保留这几类内容：

- 稳定的用户偏好，比如语言、输出风格、常用工具
- 跨会话仍然有效的事实，比如项目背景、角色信息、长期约束
- 可复用的经验，比如某类问题常见处理方式
- 对后续任务明显有帮助的重要事件

像临时情绪、一次性上下文、未经确认的猜测，一般不应该直接写进 long-term memory。

第二，存储上通常不会只用一种介质，而是分层存储：

- `KV / Profile Store`：存稳定偏好、账号信息、固定配置
- `Vector Store`：存语义检索型记忆，适合“说法不同但意思相近”的召回
- `Graph / Relation Store`：存实体关系、依赖关系、组织结构这类强关联信息

也就是说，long-term memory 通常不是一个单库，而是一套组合存储。

第三，每条记忆最好带完整 metadata，至少包括：

- 时间戳
- 来源
- 用户或租户范围
- 置信度
- 记忆类型
- 版本或状态

这样后面才能做按用户隔离、时间衰减、冲突消解和可信度判断。

第四，读取时不能只按相似度检索。更稳的做法一般是：

- 先按用户、项目、租户做 scope 过滤
- 再按 `relevance + recency` 召回
- 最后结合 importance、可信度和类型做 rerank

否则很容易召回到“语义相似但不属于当前用户”或者“很像但已经过期”的记忆。

第五，要支持更新、失效和遗忘。Long-term memory 不是只增不减，常见机制包括：

- 新信息覆盖旧偏好
- 给记忆加 TTL 或衰减权重
- 冲突时保留多版本，并标记最新有效版本
- 允许用户纠正或删除记忆

第六，要把长期记忆和结构化状态区分开。很多系统失败，不是因为没存记忆，而是把“稳定偏好”“长期事实”“任务过程状态”全部混在一个池子里，最后读出来既杂又不准。

所以比较稳的做法是：

- 长期偏好和稳定事实放 long-term memory
- 当前任务状态放 task memory
- 最近上下文放 short-term memory

**面试表达**

Long-term memory 要有效，核心不在于存得多，而在于写入要有筛选、存储要分层、读取要结合 scope、时效和相关性，另外还要支持更新、失效和用户纠正。实际工程里我一般会把稳定偏好放 KV，把可语义召回的记忆放向量库，再配合 metadata、时间衰减和 rerank，避免把过期或无关记忆召回出来。

### 15. 上下文机制的完整实现流程是什么？


**标准回答**

上下文机制我一般按“写、存、取、控”四步来讲。

第一，写入策略，也就是 memory gating。不是所有信息都进入 memory，写入时要判断它是不是长期有效、是否有复用价值、是不是稳定偏好或关键事实、是否重复。

第二，分层存储。短期上下文放会话缓存或 state store，长期记忆放向量库或 KV，任务状态放结构化 checkpoint store。

第三，读取策略。不能把所有记忆一股脑塞进 prompt，一般会按 `recency + relevance + importance + scope` 做召回。

第四，retrieval 后再做 rerank。综合关键词命中、向量相似度、时间衰减、来源可信度、memory 类型权重和 task slot 命中情况打分。

要保证状态稳定，关键在于：任务状态结构化存储、工具调用幂等记录、summary 和原始事件分层保存、冲突检测和版本控制。

**一句话版**

上下文机制不是简单拼 prompt，而是写入、存储、召回、重排和状态校验的一整套系统。

#### 补充：上下文机制的读取策略具体是什么？

上下文机制的读取策略，本质上是在回答一个问题：当前这一轮，到底该把哪些历史信息取出来放进 prompt，而不是把所有上下文一股脑塞进去。

比较稳的实现方式，一般可以分四步。

第一，先做 scope 过滤。也就是先限定读取范围，只在当前用户、当前租户、当前项目、当前任务相关的记忆里找，避免把其他用户、其他任务或者不相关知识召回进来。

这里的"用户"和"租户"是两个不同层级的概念。租户（Tenant）是组织级别的隔离单元，通常对应一家公司、一个团队或一个独立的业务实体；用户（User）是租户内部的具体个人。在多租户 SaaS 或 Agent 平台里，它们的区别是：

| 维度 | 租户 (Tenant) | 用户 (User) |
|------|--------------|-------------|
| 含义 | 一个组织、公司或团队 | 组织里的一个具体的人 |
| 隔离级别 | 硬隔离：数据、配置、权限完全独立，绝不能互通 | 软隔离：同租户内的用户可能共享部分数据 |
| 典型数据 | 知识库、API Key、计费账户、安全策略 | 个人偏好、对话历史、角色权限 |
| 泄露后果 | 严重安全事故（等于把 A 公司的数据给了 B 公司） | 隐私问题（张三看到了李四的聊天记录） |

所以 scope 过滤的顺序通常是**租户 → 项目 → 用户**，从最粗的安全边界逐步缩小到最细的个人范围。如果不做 scope 过滤，直接按语义相似度检索，就可能出现跨租户数据泄露、召回其他用户的个人偏好、或者把不相关项目的结论带进当前上下文等问题。

第二，做多维召回。读取时通常不会只按时间排序，也不会只按相似度排序，而是结合几类信号一起看：

- `recency`：最近发生的优先，适合当前对话和短期状态
- `relevance`：和当前问题最相关的优先，适合 long-term memory 和知识检索
- `importance`：高价值事实优先，比如长期偏好、关键约束、已确认结论
- `task state`：当前任务状态优先，比如做到哪一步、哪些假设已经排除

也就是说，读取策略不是只看“最近”，也不是只看“最像”，而是多维综合。

第三，召回后再做 rerank。常见会结合这些因素重新打分：

- 语义相关度
- 关键词命中
- 时间衰减
- 记忆类型权重
- 来源可信度
- 是否命中当前 task slot

比如当前是在做排障，那“最近工具结果”和“已验证结论”通常应该排在“很早以前的泛化偏好”前面。

第四，做控量和裁剪。不是召回多少放多少，而是只把最需要的内容送进 prompt。常见做法是：

- 最近几轮原文保留
- 结构化状态单独保留
- 长期记忆只取 topK
- 更久远内容用 summary 或按需 retrieval

这样可以避免上下文窗口被低价值内容占满。

**面试表达**

上下文机制的读取策略，一般不是简单按历史顺序拼接，而是先按用户、任务、租户做 scope 过滤，再结合 recency、relevance、importance 和 task state 做召回，之后通过 rerank 把最该进入当前 prompt 的内容排到前面，最后再做数量控制和裁剪。核心目标是让上下文既相关、又新鲜、还不会被噪音占满。

### 16. 超 token 怎么处理？


**标准回答**

超 token 不能只靠截断，比较稳的做法通常是“四件套”。

第一，保留最近几轮原文，确保当前对话的即时性。

第二，做 rolling summary，把较早的上下文压缩成摘要，但只保留已确认结论、未完成事项、关键约束和重要背景。

第三，做 state extraction，把目标、已完成步骤、待办、关键实体、风险项这些信息抽成结构化状态，避免它们随着摘要被丢掉。

第四，更远的历史和知识不硬塞上下文窗口，而是放进 memory 或知识库里，按需用 retrieval 拉回来。

第五，做读取策略和裁剪。即使召回回来了，也不能全量放进 prompt，而是要结合 relevance、recency、importance 和 task state 做筛选和 rerank，最后只保留最需要的内容进入上下文窗口。

第六，如果是长文档、长报告、长合同这类超长文本场景，一般会先做 chunking，再做分段摘要、分段抽取或者 map-reduce 式聚合，而不是把整篇长文本一次性塞给模型。

第七，必要时可以使用长上下文模型，但不能完全依赖。因为上下文窗口即使变大，成本、时延和注意力衰减问题依然存在，所以工程上通常还是要配合摘要、状态提取和按需检索一起使用。

**一句话版**

处理超 token 最稳的方案，不是单一摘要，而是“近期原文 + 滚动摘要 + 结构化状态 + 按需检索”的组合。

#### 补充：Rolling Summary 是什么？

`Rolling summary` 可以理解成滚动摘要或动态摘要。

它的核心思路是：当多轮对话或长任务的上下文越来越长时，不直接把旧内容丢掉，而是把较早的上下文持续压缩成一段更新中的摘要，同时保留最近几轮原文。

你可以把它理解成三层：

- 最近几轮对话保留原文
- 更早的对话不再整段保留
- 旧内容被不断合并成一份新的摘要

这份摘要通常保留的是：

- 当前目标是什么
- 已确认的结论是什么
- 已排除哪些假设
- 当前还剩哪些待办
- 有哪些不能变的约束

例如一个排障任务进行很久后，滚动摘要可能会变成：

- 当前目标：定位支付接口超时原因
- 已确认：数据库正常、Redis 正常
- 已排除：DNS 问题、单机故障
- 当前怀疑：下游依赖响应抖动
- 待办：检查网关日志和调用链路

之后随着任务继续推进，系统会把“旧摘要 + 新增对话内容”重新压成下一版摘要，这就是 rolling summary。

它的价值主要有三点：

- 控制上下文长度，避免超出 token 限制
- 保留任务连续性，不至于前面说过什么全忘掉
- 降低 token 成本，让上下文更聚焦

它的风险也很明显：

- 摘要可能丢细节
- 可能把临时假设总结成确定结论
- 如果摘要失真，后续推理会在错误上下文上继续展开

所以工程上一般不会只靠 rolling summary，而是会和结构化状态提取、按需检索和最近几轮原文保留一起使用。

**面试表达**

Rolling summary 就是在长对话或长任务里，把较早的上下文持续压缩成动态更新的摘要，保留关键目标、结论、约束和待办，而最近几轮仍然保留原文。它的作用是控制 token 长度、维持任务连续性，但要注意摘要失真风险，所以通常会和结构化状态提取、检索式 memory 一起使用。

### 17. 如果单次生成的任务量远大于模型的 Max Tokens 限制，如何实现断点继续生成？


**标准回答**

如果单次生成任务远大于模型的 max tokens 限制，我一般不会试图“一次生成完”，而是把它设计成分段生成、状态持久化、可断点续写的流程。

核心思路是：把一次长生成拆成多次可恢复的小生成，每次生成后都保存进度和状态，下次从上一次的断点继续。

一个比较稳的实现方式通常分五步。

第一，拆分生成任务。先把总任务按逻辑段落、章节、步骤或数据块切开，而不是按 token 粗暴截断。比如长报告可以拆成背景、分析、结论、建议；长代码生成可以拆成模块、文件、函数。

第二，维护结构化进度状态。通常会单独维护一个 state，比如：

- 当前生成到哪个 section
- 已完成哪些片段
- 每个片段的输出位置
- 当前任务目标和约束
- 剩余待生成内容

这样系统恢复时，不需要重新理解全量历史，只需要读状态就知道从哪继续。

第三，每一轮生成后落盘 checkpoint。每次生成完一个 chunk 或 section，就把结果和状态持久化下来，比如写数据库、对象存储或 state store。这样即使中断、超时或进程重启，也能从最近 checkpoint 继续。

第四，下一轮生成时做上下文重建。恢复时一般不会把全部已生成内容原样重新塞回模型，而是采用：

- 最近一段原文
- 已完成部分的摘要
- 当前 section 的结构化状态
- 必要的约束和全局目标

这样既能延续上下文，又不会再次超出窗口。

第五，做结果拼接和一致性校验。分段生成后，要在最终合并前检查风格是否一致、编号是否连续、前后是否矛盾、引用是否闭合、代码接口是否匹配。必要时再做一轮全局修订。

如果是更工程化一点的实现，我通常会加这些机制：

- `task_id + step_id` 标识每次生成片段
- 幂等写入，避免重复生成覆盖
- 失败重试和超时恢复
- section 级别的状态机
- 最终合并前的 verifier 或 consistency check

如果是超长文档生成，常见做法是“先 outline，再 section-by-section 生成”；如果是代码生成，常见做法是“先生成文件计划，再逐文件生成，再跑测试校验”；如果是超长摘要，常见做法是“map-reduce 或分层汇总”。

这类问题的关键不只是“续写”，而是要保证续写之后内容还能连贯、结构还正确、状态还可恢复。

**一句话版**

当任务量远大于模型上下文限制时，我一般会把它做成分段生成加 checkpoint 的流程：先按逻辑单元拆任务，维护结构化进度状态，每轮生成后落盘，再在下一轮用“最近原文 + 历史摘要 + 当前状态”重建上下文，从断点继续。核心不是一次生成完，而是可恢复、可拼接、可校验。

### 18. 在 Agent 多轮对话任务中，Attention 机制的局限性体现在哪些方面？


**标准回答**

在 Agent 的多轮对话和长任务场景里，Attention 机制虽然让模型能在一个上下文窗口里关联前后信息，但它并不等于“真正稳定的长期记忆”。它的局限性主要体现在四个方面。

第一，注意力资源是有限的，不可能对所有历史信息都同等关注。上下文一长，模型虽然理论上都能“看到”，但实际会优先关注更近、更加显著、格式更突出的内容，较早、较弱、埋得深的信息就容易被忽略。

第二，Attention 更擅长瞬时关联，不擅长稳定保存状态。也就是说，它可以在当前一次推理里把前后文关联起来，但并不等于它能像数据库一样稳定保存“关键事实”和“任务进度”。在复杂 Agent 任务里，仅靠 attention 容易导致步骤断链、约束丢失和历史结论被覆盖。

第三，长上下文下会出现注意力稀释。上下文越长，可竞争的 token 越多，重要信息和无关信息会一起进入注意力范围，结果就是模型可能把注意力分散在大量低价值内容上，导致真正关键的信息权重被冲淡。

第四，Attention 对结构混乱的上下文不够鲁棒。如果多轮对话里混杂了工具输出、系统提示、用户追问、历史摘要、代码片段、日志和文档，模型虽然都能读到，但不一定能稳定区分哪些是事实、哪些是计划、哪些是约束、哪些只是噪音。

如果放到 Agent 场景里，这些局限通常会表现为：

- 前面确认过的约束后面忘掉了
- 已排除的假设又被重新拿出来
- 工具结果已经返回，但回答里没真正利用
- 多轮任务做到一半丢失主线
- 长上下文里抓住了次要信息，却漏掉关键结论

所以工程上一般不会把 attention 当成完整 memory 机制，而会额外配：

- short-term memory
- task state
- rolling summary
- long-term memory
- retrieval
- checkpoint

也就是说，attention 解决的是“当前窗口内的信息交互”，但 Agent 需要的是“跨轮次、跨步骤、可恢复、可控的状态管理”，这两件事不能混为一谈。

**一句话版**

Attention 的局限在于，它能做上下文关联，但不等于稳定记忆。上下文一长，注意力会稀释，早期信息容易被淹没，结构混杂时也容易抓错重点，所以 Agent 不能只靠 attention，还要配合 summary、state、memory 和 retrieval。

### 19. 为什么模型在长上下文对话中容易出现”信息遗忘”？有哪些缓解机制？


**标准回答**

模型在长上下文对话里容易出现“信息遗忘”，本质上不是因为它完全看不到前文，而是因为前文虽然在窗口里，但没有稳定地被保留、强化和提取出来。

常见原因通常有五类。

第一，上下文竞争。随着对话变长，越来越多的 token 一起竞争注意力，早期信息即使还在窗口里，也可能因为位置靠前、显著性低、重复次数少而被边缘化。

第二，信息没有结构化沉淀。很多关键内容如果只是混在自然语言历史里，比如“用户明确说过不能修改数据库配置”或者“这个假设已经验证失败”，模型后续不一定能稳定再次抓到。

第三，噪音信息过多。长对话里往往混进大量无关寒暄、重复解释、冗长日志、工具输出和中间试错过程，真正关键的信息会被噪音淹没。

第四，任务状态不断变化。Agent 场景不是单轮问答，而是动态任务推进。旧计划会被新结果修正，如果没有显式状态更新机制，模型很容易同时携带旧状态和新状态，最后表现成“记混了”或“记丢了”。

第五，模型本身在超长上下文下的利用效率会下降。窗口再大，也不代表每段内容都能被同样有效地利用。上下文越长，成本越高，注意力越容易被分散，回答也越容易退化成抓局部、漏全局。

缓解机制一般会从“压缩、抽取、检索、状态化”四个方向做。

第一，做 rolling summary。把较早的对话持续压缩成摘要，只保留目标、关键结论、约束、已排除事项和待办，减少无关内容对窗口的占用。

第二，做 state extraction。把任务目标、已完成步骤、关键实体、硬约束、中间结论单独抽成结构化状态，而不是只保留在自然语言历史里。

第三，做 retrieval 和 memory。把更久远的历史、长期偏好和跨会话事实存到 memory 或知识库里，在需要的时候再按 relevance 和 recency 拉回，而不是一直硬塞在 prompt 里。

第四，做上下文读取策略。不是简单拼接历史，而是按 scope、importance、relevance、task state 做筛选和 rerank，只把当前最有价值的内容送进模型。

第五，做 checkpoint 和任务级状态保存。特别是在长任务或多步骤 Agent 里，把关键进度、已验证结论和已执行动作单独持久化，避免系统完全依赖模型“自己记住”。

第六，在长文档和超长输入场景里，优先采用 chunking、分段摘要、map-reduce、分层聚合，而不是一次把整段超长内容塞进去。

如果要总结成一句更面试化的话，我会说：

模型在长上下文里容易“遗忘”，本质上不是窗口里没有信息，而是信息没有被稳定地组织、提取和重用。所以缓解的关键不是盲目追求更大窗口，而是配合 summary、state、memory、retrieval 和 checkpoint，把重要信息从“可见”变成“可控”。

**一句话版**

长上下文里的”信息遗忘”，本质上是注意力竞争、状态未结构化和噪音过多共同造成的。缓解手段通常包括 rolling summary、state extraction、memory retrieval、上下文裁剪和 checkpoint，而不是只靠更大的 context window。

#### 补充：重锚定（Re-anchoring）是什么？

重锚定就是定期把核心目标和关键约束重新”钉”回到上下文的显眼位置，防止长会话中模型逐渐忘掉最初的重点。

长会话中容易出现”目标漂移”：前几轮目标很清晰，但随着中间讨论越来越多，早期信息的注意力权重被稀释，模型逐渐偏离最初的任务方向。这类似于一场开了三小时的会议越聊越散，需要主持人定期把大家拉回核心议题。

重锚定的做法是每隔固定轮次或在关键决策前，把当前任务状态重新注入 prompt 的高优先级位置，比如：

```
【当前任务状态提醒】
目标：定位支付接口超时原因
已确认：数据库正常、Redis 正常
已排除：DNS 问题、单机故障
当前方向：检查下游风控服务响应
约束：不能重启生产环境
```

它和其他上下文机制的区别在于：

- `Rolling Summary`：压缩旧历史，减少 token
- `State Extraction`：把关键信息抽成结构化字段
- `Checkpoint`：某个时间点的完整状态存档
- `重锚定`：把已有的关键信息**主动重复放到显眼位置**，对抗注意力衰减

重锚定的本质不是产生新信息，而是把已有的重要信息重新强调，确保模型不会因为中间内容太多而”看到了但没注意到”。

**面试表达**

重锚定是在长会话中定期把核心目标、关键约束和当前进度重新注入上下文的高优先级位置，本质是用主动重复对抗注意力衰减，防止目标漂移。它和 summary、state extraction 的区别在于，它不产生新信息，而是把已有的关键信息重新放到模型最容易注意到的位置。

#### 补充：Checkpoint 是什么？

Checkpoint 可以理解成任务执行过程中的”存档点”，类似游戏里的存档机制。它在某个时间点把当前完整的任务状态打包保存下来，后续如果出现中断、超时、上下文被压缩过度或者走错方向，就可以从最近的 checkpoint 恢复，而不用从头开始。

一个 checkpoint 通常保存的内容包括：

- 当前任务目标
- 执行进度（做到哪一步，共几步）
- 已确认结论（比如”数据库正常、Redis 正常”）
- 已排除假设（比如”排除了 DNS 问题、单机故障”）
- 待办事项（比如”下一步检查网关日志”）
- 关键上下文（最近的工具输出摘要、用户约束）

它和其他上下文机制的区别在于：

- `Rolling Summary` 关注的是历史压缩，把旧对话变成摘要
- `State Extraction` 关注的是把关键信息抽成结构化字段
- `Checkpoint` 是在某个时间点把 summary、state、关键上下文**全部打包保存**，形成一个可恢复的完整快照

checkpoint 的典型触发时机有三种：固定轮次触发（比如每 15 轮）、关键事件触发（比如完成一个子任务、用户确认了重要决策）、以及被动触发（检测到上下文即将溢出时先做一次 checkpoint 再压缩）。

**面试表达**

Checkpoint 就是任务执行过程中的状态快照。它把当前目标、进度、已确认结论、待办和关键上下文全部打包持久化，支持中断恢复和错误回滚。和 rolling summary 只压缩历史、state extraction 只抽字段不同，checkpoint 是一次完整的存档，让长任务可以在任意中断后从已知正确状态继续执行。

#### 补充：如何从 checkpoint 恢复会话？

从 checkpoint 恢复会话的核心流程是"加载快照 → 重建上下文 → 继续执行"，而不是把中断前的全部历史原样重放。

**第一步，加载 checkpoint。** 从持久化存储（数据库、Redis、对象存储等）按 `task_id + step_id` 读取最近一次 checkpoint，拿到保存的完整状态，包括目标、进度、已确认结论、已排除假设、待办事项、约束、历史摘要和最近工具结果摘要。

**第二步，重建上下文。** 不是把中断前的全部对话历史塞回 prompt，而是用 checkpoint 中的结构化状态和摘要组装一个精简但完整的新 prompt。典型结构是：

- System prompt（不变）
- 任务恢复上下文：目标、进度、已确认/已排除、待办、约束
- 历史摘要：之前阶段做了什么的压缩版本
- 最近工具结果摘要
- 用户新消息（如果有）

这样 token 消耗很小，但任务连续性完整。

**第三步，继续执行。** 模型基于重建的上下文，从中断的步骤继续推进。如果需要之前某个步骤的细节（比如第1步的具体日志），通过 retrieval 从归档的历史记录中按需召回，而不是一开始就全部加载。

工程上还有几个关键设计点：

- 过期清理：给 checkpoint 设 TTL，比如 7 天未恢复的自动清理
- 多版本保留：不只存最新一个，保留最近 N 个，支持回滚到更早的状态
- 幂等恢复：恢复时要检查上次中断的那一步是否已经执行成功，避免重复执行有副作用的操作
- 用户确认：恢复后先向用户展示当前状态，让用户确认再继续，而不是直接自动执行

和"重放全部历史"的本质区别是：重放要把中断前几十轮对话全部塞回 prompt，token 爆炸且噪音多；checkpoint 恢复只用结构化状态加摘要重建上下文，token 少、信息精准、恢复快。

**面试表达**

从 checkpoint 恢复会话，核心是"加载、重建、继续"三步。先从持久化存储读取最近的 checkpoint，再用里面的结构化状态和摘要组装一个精简的新 prompt，最后从断点继续执行。和重放全部历史的区别在于，checkpoint 恢复不需要把之前几十轮对话全部塞回去，而是用状态快照加摘要替代，token 消耗小但信息完整。工程上还要注意幂等恢复、多版本保留和恢复后的用户确认。

### 20. 假如 summary 丢失了关键细节信息，怎么办？


**标准回答**

如果 summary 丢失了关键细节，我一般不会把问题只归因于“摘要做得不够好”，而会把它当成上下文管理机制设计不完整。因为 summary 本身就是压缩，只要压缩就一定会有信息损失，关键是哪些信息不能只靠 summary 保存。

通常我会从五个方向处理。

第一，把关键状态结构化保存。像任务目标、硬约束、已确认结论、已排除假设、待办事项、关键实体，这些信息不应该只放在自然语言 summary 里，而要单独抽成结构化 state。这样即使摘要压缩了，关键信息也不会丢。

第二，摘要和原始记录分层保存。summary 只负责压缩历史，不替代原始内容。系统里最好同时保留最近几轮原文、历史 summary、关键事件日志或 checkpoint。这样一旦发现摘要信息不足，还能回查原始记录。

第三，做分层摘要。不要把所有内容都压成一段，可以拆成对话摘要、任务摘要、决策摘要、风险与约束摘要。这样比单一 summary 更不容易把不同类型的信息混掉，也更方便按需读取。

第四，给摘要增加校验机制。生成 summary 后，可以增加一次检查，比如关键约束有没有保留、已确认和已排除事项有没有写进去、当前任务阶段有没有丢、summary 是否和结构化 state 一致。必要时可以再加 verifier 复核摘要质量。

第五，按需 retrieval 回补。如果当前轮发现 summary 不够用，不要硬靠它继续推理，而是从历史对话、checkpoint、memory 或原始工具结果里再检索相关原文补回来。

如果再往工程化一点讲，我通常还会对“必须保留的信息”设明确规则，比如：

- 用户明确约束
- 已验证结论
- 已排除假设
- 高风险决策
- 外部工具返回的关键结果
- 失败原因和回滚信息

这些内容要么进入结构化状态，要么进入高优先级摘要，而不是交给普通 summary 自由压缩。

所以这类问题的核心处理思路不是“把摘要写得更长”，而是不要让 summary 独自承担全部记忆职责。

**一句话版**

如果 summary 丢失关键细节，我不会只靠改摘要模型解决，而是通过结构化 state、原文留存、分层摘要、摘要校验和按需 retrieval 来兜底。核心思路是让关键事实从”只存在于摘要里”变成”有独立状态和可追溯来源”。

### 21. 对于很长的会话，有哪些上下文管理技巧？


**标准回答**

长会话的上下文管理，核心目标是在有限窗口里始终保持”最相关、最新鲜、最关键”的信息可用。前面已经讲过 rolling summary、state extraction、memory retrieval 这些基础机制，这里重点补充工程实践中常用的管理技巧。

**一、上下文分区与预算分配**

不要把整个上下文窗口当成一个无结构的大池子，而是按功能分区，给每个区域设定 token 预算。常见的分区方式：

- `System prompt 区`：系统指令、角色定义、输出格式约束，通常固定不变
- `Structured state 区`：当前任务状态、目标、约束、已确认结论，结构化存储
- `Recent turns 区`：最近 N 轮原文，保证即时连贯性
- `Summary 区`：早期对话的滚动摘要
- `Retrieved context 区`：按需从 memory 或知识库召回的内容
- `Tool output 区`：最近工具调用结果

每个区域设 token 上限，比如 system prompt 区固定 2000 token、structured state 区最多 1500 token、recent turns 区保留 3-5 轮、summary 区不超过 2000 token。当总量接近窗口限制时，优先压缩低优先级区域（比如先压 summary 和 tool output），而不是随机截断。这样系统在任何时刻都能知道”哪些内容占了多少空间”，也能按优先级有序释放。

**二、上下文淘汰策略**

当上下文超出预算，需要有明确的淘汰策略，而不是简单丢掉最早的内容。常见策略有四种：

- `Recency-based`：最旧的内容优先淘汰，实现最简单，适合闲聊和简单问答，但对长任务容易丢关键历史
- `Importance-based`：按内容重要性评分，低重要性优先淘汰。用户明确指令、已确认结论、硬约束标记为高重要性，永远保留；中间试错、冗余解释、重复确认标记为低重要性，优先淘汰
- `Relevance-based`：按与当前任务的相关性淘汰。和当前话题无关的历史优先移出，比如当前在做排障，之前的闲聊内容可以先淘汰
- `Hybrid`：结合 recency + importance + relevance 综合打分，实际项目里最常用。比如一条信息虽然是 30 轮前说的，但它是关键约束，综合分仍然很高，就不会被淘汰

被淘汰的内容不是直接删除，而是降级到 memory 或知识库，需要时再通过 retrieval 召回。这样做既释放了窗口空间，又不会造成信息永久丢失。

**三、对话分段与话题检测**

长会话往往包含多个话题阶段，比如先讨论架构设计，再讨论数据库选型，再回到接口定义。如果不做分段管理，所有话题的上下文会混在一起互相稀释。

处理方式是在话题切换时主动做一次”阶段归档”：

- 检测到话题切换时（可以基于语义相似度下降、用户显式提出新主题、或者关键词变化），把上一阶段的关键结论、决策和状态做一次总结并归档到 memory
- 新阶段开始时，只携带全局状态（目标、约束、角色信息）和新话题相关的上下文，不带上一阶段的完整细节
- 如果用户回到之前的话题，再从归档中按需召回对应阶段的摘要和关键结论

话题检测的常见实现方式包括：监测连续轮次的 embedding 余弦相似度、检测用户显式的主题切换信号（比如”我们来聊另一个问题”）、或者用分类模型判断当前轮属于哪个话题簇。

**四、主动重锚定**

长会话进行到后半段，模型容易逐渐偏离早期确立的目标和约束，这在工程上叫”目标漂移”。原因是早期信息虽然还在窗口里，但随着中间内容堆积，注意力权重被稀释。

工程上的解决办法是做”重锚定”（re-anchoring）：

- 每隔固定轮次（比如每 10 轮）或检测到偏离时，把核心目标、关键约束、当前进度重新注入上下文的高优先级位置（比如 structured state 区的最前面）
- 在关键决策节点前，主动把相关历史结论和约束拉回到当前上下文，确保决策基于完整信息
- 使用 system prompt 或 structured state 区做持久锚点，这些区域的内容不会被 rolling summary 压缩掉
- 重锚定还可以用更直接的方式：在 prompt 里显式加一段”当前任务状态提醒”，比如”提醒：当前目标是 X，已确认约束是 Y，进度是 Z”

重锚定的本质是用主动重复对抗注意力衰减，让模型在每一轮推理时都能清楚”当前任务的核心是什么”。

**五、工具输出压缩**

在 Agent 场景里，工具输出往往占大量 token。一次数据库查询可能返回几十行表格，一次日志检索可能返回上百行原文，一次代码搜索可能返回整个文件，但其中真正有用的信息可能只有几行。

如果不做压缩，几轮工具调用后上下文就会被大量低密度信息占满。处理技巧：

- 工具返回后立即做结果提取，只保留关键字段和结论。比如数据库查询返回 50 行，只保留”共返回 50 条记录，其中异常记录 3 条，分别是 ...”
- 原始输出存到 memory、日志系统或临时存储里，上下文里只放摘要版本。如果后续需要细节，再通过 retrieval 从原始输出里召回
- 对于表格数据，只保留与当前问题相关的列和行
- 对于日志输出，只保留包含关键信息的行和上下文
- 对于代码搜索结果，只保留匹配的函数签名和关键片段，不保留整个文件

工具输出压缩的时机也很重要：最好在工具返回后立即压缩，而不是等到上下文快满了再集中处理，因为那时候已经浪费了很多轮的窗口空间。

**六、KV Cache 复用**

在工程层面，如果使用支持 KV cache 的推理框架（比如 vLLM、TGI、TensorRT-LLM），长会话的前缀部分可以缓存复用，避免每轮都重新计算整个 prompt 的 attention。

优化技巧：

- 把不变的 system prompt 和长期稳定的 structured state 放在 prompt 最前面，最大化 prefix cache 命中率
- 频繁变化的内容（最近对话、工具输出）放在末尾，这样前缀部分在多轮之间保持不变，cache 可以持续复用
- 注意 cache 失效策略：当 structured state 更新时，需要从更新位置开始重新计算，所以 state 更新频率不宜过高
- 在多用户场景里，如果多个用户共享相同的 system prompt，可以做 system prompt 级别的 cache 共享，进一步降低计算成本

KV cache 复用不直接影响上下文质量，但它大幅降低了长会话的推理延迟和成本，让”保留更多上下文”在工程上变得更可行。

**七、会话级 checkpoint**

对于特别长的任务型会话（比如持续数十轮的排障、多步骤的代码重构），建议在关键节点做显式 checkpoint：

- 在每个重要阶段完成后，保存当前完整状态快照：任务目标、当前进度、已确认结论、待办事项、关键上下文、活跃约束
- 如果会话中断（网络断开、session 超时、用户离开后回来）或上下文被压缩过度，可以从最近 checkpoint 恢复，而不是从零开始
- checkpoint 之间的详细历史可以安全归档到 memory 或日志，不需要始终保留在上下文里
- checkpoint 还可以用于错误恢复：如果 Agent 在某一步走错了方向，可以回滚到上一个 checkpoint 重新开始，而不是带着错误状态继续

checkpoint 的触发时机通常有三种：固定轮次触发（比如每 15 轮）、关键事件触发（比如完成一个子任务、用户确认了重要决策）、以及被动触发（检测到上下文即将溢出时先做一次 checkpoint 再压缩）。

**八、多层摘要**

不要用一份 summary 覆盖所有历史，而是分层维护，不同粒度的摘要服务不同的查询需求：

- `Turn-level summary`：每轮对话的要点提取，粒度最细，保留具体细节。比如”用户问了接口超时原因，模型分析了三种可能性，排除了 DNS”
- `Phase-level summary`：每个话题阶段的总结，粒度适中，保留阶段性结论和决策。比如”排障第一阶段：确认数据库正常，排除网络问题，锁定下游服务”
- `Session-level summary`：整个会话的全局摘要，粒度最粗，保留最终结论和全局目标。比如”本次会话目标是定位支付超时，最终确认是下游风控服务响应抖动”

读取时按需组合：需要回顾具体细节看 turn-level，需要了解某个阶段做了什么看 phase-level，需要全局视角看 session-level。这样比单一 summary 更不容易丢关键信息，也更方便在不同场景下选择合适的信息密度。

更新策略上，turn-level 每轮更新，phase-level 在话题切换时更新，session-level 在关键节点或会话结束时更新。

**一句话版**

长会话的上下文管理，核心技巧是分区预算、智能淘汰、话题分段、主动重锚定、工具输出压缩、KV cache 复用、会话 checkpoint 和多层摘要。本质上不是靠更大窗口解决，而是用工程手段让有限窗口里始终保留最该保留的内容。

**面试表达**

长会话上下文管理我一般从八个方面做。第一是上下文分区和预算分配，把窗口按功能分成 system、state、recent、summary、retrieved、tool output 几个区域，各设 token 上限，超限时按优先级有序释放；第二是上下文淘汰策略，按 recency + importance + relevance 综合打分决定淘汰顺序，淘汰的内容降级到 memory 而不是直接删除；第三是话题分段，检测到话题切换时归档旧阶段结论，新阶段只携带全局状态，避免不同话题互相稀释；第四是主动重锚定，定期或在关键决策前把核心目标和约束重新注入高优先级位置，对抗注意力衰减导致的目标漂移；第五是工具输出压缩，工具返回后立即提取关键信息，原始输出存 memory，上下文只放摘要；第六是 KV cache 复用，把不变内容放 prompt 最前面最大化缓存命中，降低长会话推理成本；第七是会话级 checkpoint，关键节点做完整状态快照，支持中断恢复和错误回滚；第八是多层摘要，turn、phase、session 三层按需组合读取，避免单一 summary 丢信息。核心思路不是追求更大窗口，而是用工程手段确保有限窗口里始终保留最关键的信息。

## 四、Agent 规划、架构与多 Agent 协作

### 21. Agent 和 Workflow 的区别是什么？什么场景选哪种？


**标准回答**

Workflow 更像预先编排好的固定流程，路径基本确定，强调可控、稳定和可审计；Agent 更像给定目标后自主规划和决策，强调灵活性、探索能力和长链路任务处理。

简单说，Workflow 适合“已知路径的问题”，Agent 适合“已知目标但未知路径的问题”。

我通常在以下场景优先选 Workflow：

- 流程固定、规则明确
- 合规要求高、必须强审计
- 错一步代价高
- 输入输出格式稳定

像审批流、工单流转、固定报表生成，更适合 Workflow。

以下场景更适合 Agent：

- 任务目标明确但路径不固定
- 需要多步推理、多轮试错
- 需要自主搜索、调用工具、整合信息
- 用户表达模糊，任务拆解依赖模型判断

像智能排障、代码修复、research、复杂客服问答，更适合 Agent。

企业里通常不是二选一，而是 Agent 负责决策，Workflow 负责约束和落地。

**一句话版**

Workflow 解决确定性流程，Agent 解决不确定性任务，成熟系统一般是两者结合，而不是对立关系。

### 22. 企业级 Agent 架构怎么设计？安全、隔离、权限、审计、日志怎么做？


**标准回答**

企业级 Agent 不应该设计成“大模型直连一堆工具”，更稳妥的方式是分层、分组件、强边界。

一个典型拆法是：

- `BFF / Agent Gateway`：统一接前端、IM、API，做会话管理、身份识别、限流和多租户上下文注入
- `Agent Orchestrator`：负责任务拆解、状态机控制、prompt 组装、模型路由、memory 读写和失败重试
- `Tool Server / MCP Server`：把搜索、数据库、知识库、工单系统、邮件、浏览器等能力统一封装
- `Worker / Sandbox`：专门执行有副作用的动作，比如跑 shell、改文件、调浏览器、执行脚本
- `Memory / Knowledge Layer`：管理 short-term、long-term、task memory 和 RAG
- `Observability / Governance`：管理 trace、审计、成本、风险、回放和反馈闭环

安全和隔离上，关键是：

- 所有工具调用都必须带用户身份、租户和 scope
- 执行动作放到隔离容器或沙箱，配资源限制、网络白名单、命令白名单和超时
- 检索前后都做权限控制，避免越权数据进入上下文
- 高风险动作做审批和 human-in-the-loop

审计上至少要回答四件事：谁发起的、Agent 做了什么、调了哪些工具、为什么这么做。日志上不要只记模型输出，要记全链路，包括 trace id、task id、模型版本、prompt 模板版本、memory 命中、retrieval 结果、tool latency 和 token 成本。

**一句话版**

企业级 Agent 架构的重点不是把模型接进去，而是把理解、决策、执行解耦，再通过权限、隔离、审批和审计把风险关进笼子里。

#### 补充：企业级 Agent 架构怎么设计？详细回答

如果让我设计企业级 Agent 架构，我一般不会做成“大模型加一堆工具直连”的单体模式，而会拆成一个分层、可控、可审计的系统。因为企业场景真正难的不是让模型会回答，而是让它在权限、安全、执行、副作用、稳定性这些约束下还能可靠做事。

一个比较稳的设计思路，可以分成七层。

第一层是接入层，也就是 `BFF / Agent Gateway`。这一层负责统一接前端、IM、Web、OpenAPI 等入口，主要做用户认证、租户识别、会话管理、请求标准化、限流和流式输出。它的核心作用是把“谁发起的、代表谁执行、属于哪个租户、是否有权限”这些上下文先固定下来，后面所有模块都基于这个上下文运行。

第二层是 `Orchestrator`，也就是 Agent 的控制中枢。这一层不建议只靠一段 prompt 驱动，而更适合做成可观察的状态机或 DAG 编排器。它主要负责任务拆解、子任务调度、模型路由、prompt 组装、tool call 决策、memory 读写、错误恢复和终止条件控制。比如用户说“帮我定位昨天支付接口异常并给出修复建议”，Orchestrator 应该先拆成取时间范围、拉监控、查日志、形成假设、验证假设、生成报告这样几个步骤，而不是一次性让模型自由发挥。

第三层是模型服务层，也就是 `Model Layer`。企业级 Agent 通常不会绑定单一模型，而是会做模型路由。简单分类、提取、判断类任务可以走低成本模型；复杂推理、代码修改、长上下文分析可以走强模型。这一层除了模型调用，还要负责 fallback、超时控制、重试策略、token 成本统计和供应商健康状态监控。

第四层是工具接入层，也就是 `Tool Layer` 或 `Tool Server / MCP Server`。这一层的目标是把搜索、数据库、知识库、工单系统、邮件、浏览器、文件系统、脚本执行这些外部能力统一封装，而不是让模型直接碰内部系统。每个工具最好都要明确定义输入参数、输出结构、权限边界、是否只读、是否有副作用、超时和幂等要求。

第五层是执行层，也就是 `Worker / Sandbox`。所有有副作用的动作，比如跑 shell、改文件、执行 SQL、调用内部写接口、自动化运维脚本，都尽量放到隔离环境里执行，而不是在主控制进程里直接做。这里一般会配容器隔离、文件系统隔离、网络白名单、资源限制、执行超时和命令白名单。原因很简单，企业级 Agent 最危险的不是“答错”，而是“做错”。

第六层是 `Memory / Knowledge Layer`。这一层既包括 short-term memory、task memory、long-term memory，也包括 RAG 能力。short-term memory 负责最近对话和最近工具结果，task memory 负责当前任务做到哪一步、哪些假设验证过，long-term memory 负责用户偏好、稳定事实和长期约束。如果有企业知识问答，还会加上文档解析、向量索引、倒排索引、混合检索、rerank 和引用管理。它的目标不是“存更多”，而是“在当前任务里取对”。

第七层是 `Observability / Governance`，也就是可观测和治理层。这层在企业级 Agent 里非常关键，但最容易被忽略。至少要能记录 trace id、task id、conversation id、prompt 版本、模型版本、tool call、memory 命中、retrieval 结果、rerank 结果、决策路径、token 成本、延迟、错误率、审批记录和最终动作结果。没有这层，系统出了问题以后基本就是黑盒。

如果讲安全、权限和审计，我一般会重点强调四件事。

第一，权限控制。所有 Agent 行为都必须绑定真实用户身份，不能让 Agent 默认拿系统超级权限替所有人做事。常见做法是 `RBAC / ABAC`、工具级 scope 控制、delegated auth，每次调用都带 user、tenant、project 上下文，高风险操作要二次确认或审批令牌。

第二，数据隔离。必须避免跨租户数据泄露、越权检索、工具返回敏感信息污染 prompt，以及不同用户之间的上下文串扰。通常要做检索前权限过滤、输出脱敏、工具结果 sanitize 和 memory 分租户隔离。

第三，动作分级。一般会把动作分成只读动作、低风险写动作和高风险动作。只读动作可以自动执行，低风险写动作要求确认，高风险动作必须审批。有些极高风险动作，比如删数据，在很多企业场景下会被直接禁掉。

第四，审计。审计日志至少要回答四个问题：谁发起的、Agent 做了什么、调了什么工具、为什么这么做。所以建议记录原始请求、计划步骤、工具调用入参和出参摘要、关键决策理由、审批记录、执行结果和回滚记录。

如果从一次典型请求来讲，整个调用流程一般是这样的：

1. 用户发起任务。
2. Gateway 做鉴权并注入租户、权限和会话上下文。
3. Orchestrator 拆任务并读取 memory 和知识。
4. 系统根据任务类型路由到合适模型。
5. 如果需要外部能力，就调用 Tool Server。
6. 有副作用的动作进入 Sandbox Worker 执行。
7. 执行结果回流给 Orchestrator。
8. Orchestrator 判断是否继续下一步、是否需要人工确认。
9. 最终输出结果，同时把 trace、日志、审计记录和成本数据落下来。

所以我对企业级 Agent 架构的理解是，重点不是把模型接进去，而是把理解、决策、执行和治理拆开。模型负责推理，工具负责能力，沙箱负责隔离，治理层负责风险控制和可回放，这样整个系统才真正能进企业环境。

**详细回答总结版**

如果让我设计企业级 Agent 架构，我会采用分层、分组件、强边界的方式。入口层负责身份、租户和会话管理；Orchestrator 负责任务拆解、状态机和模型路由；Tool Server 统一封装外部能力；有副作用的动作放到隔离 Worker 或沙箱执行；Memory 和 RAG 负责上下文与知识支持；最后通过 observability 和 governance 做全链路日志、审计、成本、风险和回放。核心目标不是让模型直接连所有系统，而是把理解、决策、执行解耦，再通过权限、隔离、审批和审计把风险关住。

#### 补充：什么是有副作用的动作？

有副作用的动作，指的是执行之后会真正改变外部环境、系统状态、数据或资源的操作，而不只是读取、查看或分析信息。

可以简单理解成：

- 只读动作：看，不改
- 有副作用动作：会改，会留下结果

常见的有副作用动作包括：

- 重启服务
- 修改配置
- 写数据库
- 删数据
- 发邮件、发消息
- 创建工单
- 调用内部写接口
- 改文件
- 执行脚本
- 切流、扩容、回滚

相对地，像查询日志、查监控、读数据库、搜知识库、查看文件内容，这些通常属于无副作用或低副作用动作。

企业级 Agent 特别强调这个概念，是因为模型“答错”和 Agent“做错”不是一个风险等级。回答错了，最多是建议有偏差；但如果 Agent 自动执行了一个错误的有副作用动作，就可能直接造成生产事故。

所以工程上通常会对这类动作单独做约束，比如：

- 放到 sandbox 或隔离 worker 里执行
- 做权限校验
- 做审批和 human-in-the-loop
- 做幂等控制
- 做审计日志
- 做超时和回滚保护

**面试表达**

有副作用的动作，就是执行后会改变系统状态、数据或外部环境的操作，比如写库、改配置、重启服务、发消息、执行脚本等。它和只读操作的区别在于，前者会产生真实影响，所以在企业级 Agent 里通常要单独做隔离、审批、审计和风险控制。

#### 补充：动作在沙盒里执行完之后，一般还会做什么？

在沙盒里执行完之后，通常不会直接算任务结束，后面一般还会有一整套收尾和控制动作。

第一，收集执行结果。包括标准输出、标准错误、退出码、生成的文件、运行时长、资源占用等，把这些结果从沙盒环境里收回来。

第二，做结果校验。执行成功不等于任务成功，还要判断结果是否符合预期。比如命令是否返回成功、文件是否真的改对了、测试是否通过、输出格式是否正确、有没有触发安全规则或越权行为。

第三，回传给 `Orchestrator`。沙盒本身只负责执行，执行完后要把结果回传给编排层，由 Orchestrator 决定下一步是继续、重试、换工具、升级模型还是结束任务。

第四，记录审计和日志。企业场景里通常要把这次执行的关键信息记下来，比如谁触发的、执行了什么动作、输入输出摘要、是否成功、是否产生副作用、耗时和资源消耗。

第五，做清理和回收。包括清理临时文件、销毁临时容器、释放临时凭证、回收资源、关闭临时网络权限，避免状态残留影响后续任务，也避免安全风险。

如果是高风险动作，通常还会多两步：

- 做人工确认后的正式提交
- 做回滚准备，或者在失败时触发回滚

**面试表达**

动作在沙盒里执行完之后，一般不会直接结束，而是先收集输出和退出状态，再做结果校验，然后把结果回传给 Orchestrator 决定下一步。同时还要记录审计日志，并清理临时环境和凭证。如果是高风险动作，还会加确认、回滚和后置安全检查。

### 23. Agent 系统中的 LangGraph 是如何搭建的？其 Memory 组件的工作机制是怎样的？


**标准回答**

如果用 LangGraph 来搭 Agent，我一般会把它理解成“用图来组织 Agent 的状态流转和节点执行”，而不是单纯把几个 prompt 串起来。

LangGraph 的核心搭建思路通常有四步。

第一，定义 `State`。也就是先定义整个 Agent 在执行过程中要维护哪些状态字段。常见会包括：

- 用户输入
- 当前计划
- 中间结果
- 工具调用记录
- 检索结果
- 最终输出
- 错误信息
- 是否结束

这一步很重要，因为图里的每个节点本质上都是“读取状态 -> 更新状态”。

第二，定义节点，也就是 `Node`。每个节点通常代表一个明确职责，比如：

- Planner：生成或更新计划
- Retriever：查知识库
- Tool Executor：调用工具
- Critic / Verifier：校验结果
- Responder：生成最终回答

节点的输入是当前 state，输出通常是对 state 的增量更新。

第三，定义边和路由逻辑。也就是决定节点之间怎么流转。常见会有：

- 固定顺序边
- 条件边
- 循环边
- 终止条件

比如 Planner 生成计划后，如果需要查知识就走 Retriever；如果需要调工具就走 Tool Executor；如果结果不满足要求，还可以回到 Planner 或 Critic 继续迭代。

第四，挂上 checkpoint 和持久化。企业级使用里一般不会只跑一张纯内存图，而会配状态持久化和中断恢复能力，方便多轮任务和长任务执行。

如果用工程化语言来讲，LangGraph 比较适合解决的是：

- Agent 多步骤编排
- 条件分支与循环
- 中断恢复
- 可观测状态流转
- 人工介入节点

它比简单链式调用更适合复杂任务，因为复杂任务往往不是直线，而是带判断和回路的。

再说 Memory 的工作机制。这里可以分成两个层次理解。

第一层是图内状态，也可以理解成运行时 memory。它主要是当前一次执行过程中的工作记忆，通常直接存在 graph state 里，比如当前目标、已完成步骤、中间结果、最近工具输出。这部分更像 short-term memory 或 task memory。

第二层是图外持久化 memory。也就是把会话历史、长期偏好、任务 checkpoint、已确认结论等内容持久化到外部存储里，在后续节点或下次会话中再读回来。这部分更像 long-term memory。

从工作机制上看，Memory 一般是这样参与图执行的：

1. 图启动前，先从外部 memory 读取与当前用户、当前任务相关的历史信息。
2. 把这些信息注入到初始 state 中。
3. 图执行过程中，节点不断更新 state。
4. 在关键节点或结束节点，把新的状态、摘要、偏好、结果写回持久化 memory。
5. 下次再运行时，再按 scope、relevance、recency 把相关 memory 取回来。

如果进一步拆，LangGraph 场景下常见会同时存在三类 memory：

- `Working Memory`：当前 state 里的即时上下文
- `Checkpoint Memory`：图执行过程中的中间状态快照，用于断点恢复
- `Long-term Memory`：跨会话长期保留的偏好、事实和经验

所以 Memory 在 LangGraph 里不是单独一个“聊天历史组件”，而是运行时状态、检查点和长期记忆的组合。

**一句话版**

LangGraph 的本质是用状态图来组织 Agent 的多步骤执行，每个节点读取和更新 state，边负责控制流。它的 Memory 机制既包括图内的运行时状态，也包括图外的 checkpoint 和长期记忆，核心目标是让 Agent 在复杂任务里既能推进，又能恢复，还能跨轮次延续上下文。

### 24. 多 Agent 怎么实现，Agent 之间如何通信？


**标准回答**

多 Agent 的核心不是“多开几个模型”，而是把不同职责拆成不同角色，再通过编排层、共享状态和明确协议把它们串起来。

常见拆法是：

- `Planner Agent`：负责任务拆解和全局计划
- `Executor Agent`：负责执行子任务、调用工具和产出中间结果
- `Verifier / Critic Agent`：负责校验事实、检查冲突和挑错
- `Writer / Synthesizer Agent`：负责汇总结果、整理成最终输出
- `Supervisor / Orchestrator`：负责调度、状态机、预算、超时、重试和终止条件

如果让我做工程实现，我一般不会让 Agent 之间自由对话，而是优先走“受控通信”。

第一种方式是通过 `Orchestrator` 中转，也叫星型拓扑。所有 Agent 只和编排器通信，不直接互相发消息。编排器负责接收上游结果、决定下一步调谁、传什么上下文。比如 Planner 输出子任务列表后，编排器逐个分发给 Executor；Executor 返回结果后，编排器决定是交给 Verifier 校验，还是直接交给 Writer 汇总。整个过程中 Agent 之间没有直接连线，所有信息流都经过编排器这个中心节点。好处是链路清晰、易审计、便于统一做权限控制、重试、超时和预算管控。缺点是编排器本身成为单点瓶颈，如果 Agent 数量多或者需要频繁交互，编排器的逻辑会变得很复杂。实际工程中大多数多 Agent 系统都优先用这种方式，因为可控性最高。

第二种方式是通过共享状态或黑板机制通信。核心思路是所有 Agent 共享一块结构化的状态空间——可以叫 `task state`、`blackboard` 或者 `shared context`——每个 Agent 执行完后把自己的产出写入对应字段，其他 Agent 在被调度时从中读取自己需要的部分。比如 Planner 把拆解出的子任务列表写进 `subtasks` 字段，Executor 读取待执行的子任务并把结果写入 `results` 字段，Verifier 读取 `results` 并把校验结论写入 `verification` 字段。这种方式下 Agent 之间不需要知道彼此的存在，通信完全通过数据结构解耦。LangGraph 的 `State` 就是这种模式的典型实现——每个节点函数读写同一个 TypedDict，边只负责控制流转顺序。好处是天然支持异步执行和并行协作，因为多个 Agent 可以同时读写不同字段；也方便做断点恢复，因为状态本身就是可序列化的快照。缺点是需要提前设计好状态结构，字段权限和冲突解决策略也需要考虑——比如两个 Agent 同时写同一个字段时用覆盖还是追加。

第三种方式是通过消息队列或事件总线通信，也就是发布-订阅模式。每个 Agent 在完成动作后发布一个结构化事件，比如 `subtask_completed`、`evidence_found`、`verification_failed`，由订阅了该事件的其他 Agent 异步消费。比如 Executor 完成子任务后发布 `subtask_completed` 事件，Verifier 订阅了这个事件就会自动被触发去做校验；如果校验失败，Verifier 发布 `verification_failed`，编排器或 Executor 订阅后决定是重试还是升级。底层可以用内存队列、Redis Pub/Sub、Kafka 或者云消息服务实现。这种方式最适合长时间运行的任务、需要并行执行的场景和分布式部署，因为 Agent 之间完全松耦合，可以独立扩缩容。缺点是复杂度最高——需要处理消息丢失、重复消费、顺序保证等分布式问题，调试和追踪也比前两种方式困难，通常需要配套 trace_id 串联和事件溯源机制。

通信协议上，我通常会把消息做成结构化格式，而不是只传一段自然语言。最少会包含这些字段：

- `schema_version`
- `trace_id` / `task_id` / `step_id`
- `sender` / `receiver`
- `message_type`
- `goal` / `subtask`
- `payload`
- `status`
- `confidence`
- `evidence_refs`
- `timestamp`

这样设计的原因有四个：

- 方便幂等、重试和去重
- 方便状态回放和审计
- 方便做权限隔离和多租户控制
- 方便把结论和证据绑定，避免只传口头判断

但多 Agent 也不是越多越好。角色越多，延迟、token 成本、协调开销和错误传播链路都会增加。简单任务我一般更倾向单 Agent + 工具调用，只有在任务明显可分工、需要交叉校验或需要并行研究时，才会上多 Agent。

**一句话版**

多 Agent 的本质是“角色拆分 + 编排控制 + 共享状态 + 明确协议”，而不是让多个模型自由聊天。工程上优先受控通信，避免黑盒协作。

### 25. 为什么要用 Planning & Solve 架构？还了解哪些架构？ReAct 和 Reflexion 怎么理解？


**标准回答**

`Planning & Solve` 的核心思想是先做全局规划，再按计划逐步执行。它适合长链路、强依赖、对可控性和可审计性要求高的任务。

为什么很多场景会用它，主要有四个原因。

第一，它能把大任务拆成若干可验证的小步骤。相比直接端到端生成，出错时更容易定位在哪一步失真。

第二，它更适合插入预算、审批、重试、回滚和人工确认。也就是说，它天然适合工程化治理，而不只是模型自由发挥。

第三，它能减少“想到哪做到哪”的漂移。尤其在复杂任务里，如果没有先规划，模型很容易局部最优、重复试错或者把步骤顺序搞乱。

第四，它更容易做多 Agent 协作。因为有了 plan，后面就能把不同子任务分给不同 Agent 并行或串行处理。

除了 `Planning & Solve`，我还比较熟悉这些架构：

- `ReAct`：推理和行动交替进行，典型模式是 `think -> act -> observe`
- `Plan-Execute`：先出计划，再由执行器按计划跑
- `Workflow / State Machine`：适合确定性强、流程固定的任务
- `Supervisor-Worker`：适合多 Agent 分工和集中调度
- `Tree of Thoughts`：适合需要多分支搜索和方案比较的任务
- `Critic / Verifier`：适合在结果产出后做事实核查和纠错
- `Graph / DAG`：适合复杂节点编排和可恢复执行

`ReAct` 来自 2022 年 Yao 等人的论文，全称是 Reasoning + Acting。它的核心思路是让模型在推理和行动之间交替进行，形成 `Thought → Action → Observation` 的循环。每一步模型先用自然语言”想一想”当前状态和下一步该做什么（Thought），然后执行一个具体动作比如调用搜索引擎、查数据库、调 API（Action），再观察动作返回的结果（Observation），基于观察结果进入下一轮思考。这个循环持续到模型判断任务完成为止。

ReAct 的优点在于灵活性强。它不需要预先规划完整路径，特别适合信息不完整、需要边查边做的场景——比如多跳问答（先查 A，根据 A 的结果再查 B）、需要动态选择工具的任务、以及开放式探索型任务。相比纯 Chain-of-Thought 只在脑子里推理，ReAct 能通过实际行动获取外部信息来修正推理方向。

但 ReAct 也有明显的局限。第一，它容易陷入局部路径——模型可能在某个方向上反复尝试，缺乏全局视角来判断是否该换条路。第二，轨迹可能很长，工具调用次数不可预测，导致 token 消耗和延迟难以控制。第三，没有外部约束时过程不够稳定，同样的任务可能跑出完全不同的执行路径。第四，它本质上是贪心的——每一步只基于当前观察决策，不会回头修正之前的错误判断。

`Reflexion` 来自 2023 年 Shinn 等人的论文，它解决的是 ReAct 类 Agent “犯了错不会学”的问题。核心思路不是简单的”再想一遍”，而是在一轮执行完成后，专门做一次结构化的失败反思，把失败原因、改进方向和经验教训写成一段显式的文本反馈（叫 self-reflection），然后把这段反馈作为额外上下文注入下一轮尝试。

具体流程是：Agent 先执行一轮任务（用 ReAct 或其他方式），执行完后由一个 Evaluator 判断结果是否达标。如果失败，Agent 进入反思环节，生成一段类似”上一轮失败是因为第 3 步查错了数据源，下次应该先验证数据源的时效性”这样的总结。这段反思会存入一个 memory buffer，下一轮执行时作为 prompt 的一部分传入，这样 Agent 就能”带着经验”重新尝试，而不是从零开始犯同样的错误。

Reflexion 的价值在于把”从失败中学习”这件事显式化了。传统的重试只是简单重跑，Reflexion 的重试是带着上一轮的教训重跑。实验表明它在编程任务（HumanEval）、决策任务（AlfWorld）和推理任务上都能显著提升多轮成功率。

但 Reflexion 也有明确的边界：

- 每轮反思都需要额外的 LLM 调用，增加 token 消耗和延迟成本，通常比单轮执行贵 2-3 倍
- 如果没有外部 Evaluator 或 Verifier 提供客观判断，模型的自我反思可能只是自我说服——它可能认为自己改对了，实际上只是换了一种方式犯错
- 如果反思内容本身就是错的（比如归因错误），还会把错误结论固化进后续流程，导致越改越偏
- 它更适合有明确成功/失败判断标准的任务，对于开放式、没有标准答案的任务效果有限

所以我一般会这样选：

- 任务链路长、步骤依赖强、需要审计时，用 `Planning & Solve`
- 任务动态性强、工具交互多时，用 `ReAct`
- 任务允许多轮尝试、且失败复盘价值高时，加 `Reflexion`
- 流程高度确定时，用 `Workflow / State Machine`

#### 补充：子任务递归拆分的终止条件和具体执行

在 Planning & Solve 架构里，任务拆解天然是递归的——一个子任务可能还能继续拆。如果不设终止条件，系统要么无限递归，要么拆出一堆粒度不一致的碎片。

我一般从四个维度判断一个子任务是否已经足够原子。第一，单工具可完成，一次工具调用就能拿到结果。第二，单模型单轮可回答，不需要多轮推理和外部信息。第三，无内部依赖，子任务内部没有"先做 A 才能做 B"的串行关系。第四，结果可直接验证，输出有明确的成功/失败标准。再加一条硬性兜底：最大递归深度 3-4 层，单次拆分最多 5-7 个子任务，超过就强制交给执行器。

具体执行上，我不会用代码层面的函数递归，而是用任务队列加循环来模拟，因为递归调用栈不好做持久化、超时控制和断点恢复。

流程是：维护一个任务队列和深度表。每次取出一个任务，先判断是否原子。是原子任务就直接执行，结果写入共享状态；不是原子任务就调 Planner 拆分，子任务追加深度计数后放回队列；深度到上限的强制执行。

拆分时 Planner 带着约束拆：每个子任务必须有明确的输入和预期输出格式，子任务之间的依赖关系必须显式标注，每个子任务附带一个 `is_atomic` 布尔判断让 Planner 自己先评估。

拆完之后按依赖关系构建 DAG，没有依赖的并行执行，有依赖的等上游完成再触发。如果某个子任务执行失败，把失败信息交回 Planner 决定是重试、换工具还是重新拆分，这就是动态重规划的入口。如果系统支持 re-planning，还可以先粗拆，执行中发现子任务太大再按需细化，比一开始追求完美拆分更实用。

**一句话版**

`Planning & Solve` 强在全局可控，`ReAct` 强在动态交互，`Reflexion` 强在失败后复盘。实际系统里通常不是三选一，而是组合使用。子任务拆分用任务队列加 DAG 调度代替真递归，终止条件是"单工具可完成、单轮可回答、无内部依赖、结果可验证"加最大深度兜底。

### 26. Agent 的数据格式怎么设置？包含什么元素？为什么要这么设计？


**标准回答**

Agent 系统里，数据格式本质上是“运行时契约”。如果输入输出只靠自然语言描述，系统很快会变成不可验证、不可审计、不可重试的黑盒。

所以我通常会把关键输入输出做成结构化 schema，而不是让上下游只传一段 prompt。

一个比较完整的结构，通常会包含这些元素：

- `schema_version`：方便协议演进和兼容旧数据
- `trace_id` / `conversation_id` / `task_id` / `step_id`：方便追踪完整链路
- `sender` / `receiver` / `agent_role`：说明是谁发的，给谁处理
- `goal` / `subtask`：明确当前任务目标和子任务边界
- `context`：必要上下文，但要和外部不可信内容分层
- `constraints`：时间、预算、权限、格式、风险等级等约束
- `tool_calls` / `tool_results`：记录调用了什么工具、参数是什么、返回了什么
- `evidence_refs`：引用哪些证据、文档、日志、网页或工具结果
- `status`：如 `pending`、`running`、`blocked`、`completed`、`failed`
- `confidence`：给后续 verifier 或 orchestrator 作为参考
- `expected_output_schema`：约束下游返回格式
- `timestamp` / `ttl`：控制时效和过期数据
- `metadata`：来源、租户、权限范围、风险标签等

为什么要这么设计，主要有五个原因。

第一，方便编排。编排器需要知道当前任务做到哪一步、下一步交给谁、失败后怎么恢复。

第二，方便幂等与重试。没有 `task_id`、`step_id` 和明确状态，很难判断某一步是没执行、执行失败，还是已经执行过了。

第三，方便权限和隔离。尤其企业场景里，要明确哪些上下文是系统生成的，哪些是外部输入的，哪些工具结果可读，哪些动作有副作用。

第四，方便审计和回放。后面出了问题，必须能回看某一步是基于什么输入、调用了什么工具、得出了什么结论。

第五，方便把结论和证据绑定。没有 `evidence_refs`，模型很容易只给出判断，不给依据。

工程上我一般会坚持一个原则：自由文本可以有，但它只是 `content/payload` 的一部分，不能代替整个协议。系统真正依赖的是结构化字段，而不是模糊自然语言。

**一句话版**

Agent 的数据格式本质上是运行时契约，核心目标不是“好看”，而是让系统可编排、可重试、可审计、可验证。

### 27. 如何分配子任务？有哪些具体措施？


**标准回答**

我理解子任务分配不是“把任务平均切几块”，而是在目标、依赖、能力、风险和成本约束下做任务调度。也就是说，先明确任务结构，再决定由谁做、按什么顺序做、哪些可以并行做。

如果让我落到工程上，我通常会做这些具体措施。

第一，做任务模板化拆解。不是让模型只输出一串自然语言计划，而是要求每个子任务至少包含这些字段：

- `goal`
- `input`
- `expected_output`
- `depends_on`
- `owner`
- `risk_level`
- `done_criteria`
- `evidence_required`

这样做的好处是后面才能继续做调度、重试和验收，而不是只得到一份“看起来像计划”的文本。

第二，做能力路由矩阵。也就是先把任务类型和 Agent 能力建立映射，而不是临场拍脑袋分配。比如：

- 搜索和资料收集交给 `Researcher`
- 分析归因交给 `Analyst`
- 事实核查交给 `Verifier`
- 结果整理交给 `Writer`
- 有副作用的动作交给受控 `Executor` 或人工审批链路

第三，做依赖图或 DAG。也就是把前置依赖明确标出来，没依赖的并行，有依赖的串行。比如“查监控”和“查日志”可以并行，但“形成根因判断”必须等前面的证据回来再做。

第四，做并行判定规则。不是所有任务都值得并行。我通常会要求满足这几类条件才并行：

- 数据源不同
- 输出互不依赖
- 失败不会互相污染
- 汇总成本低于串行等待成本

第五，做风险分级分配。读、写、执行、审批要分层。低风险读任务可以自动并行，高风险写任务不能混在普通分析任务里，而要单独分配给受控执行器。

第六，做预算约束。每个子任务在分配时就带上 `time budget`、`token budget`、`tool call limit`、`cost limit`。这样可以避免某个子任务无限扩张，拖垮整个任务链路。

第七，做去重和合并。如果两个子任务查询的是同一个系统、同一时间窗口、同一类指标，我会优先合并，避免重复调用工具和重复消费上下文。

第八，做动态重规划。任务执行过程中如果发现关键前提不成立、证据不足或某条路径被阻塞，就触发 replanning，而不是让原计划机械执行到底。

第九，做状态看板。每个子任务都要有 `pending`、`running`、`blocked`、`completed`、`failed` 这类状态，否则编排器不知道下一步应该推进、等待还是回退。

第十，做结果回流。执行完成后，把成功率、重试率、平均耗时、是否阻塞后续任务这些信息回流给 planner，逐步优化拆分和分配策略。

所以我理解“如何分配子任务”，本质上不是平均切分，而是按“能力匹配、依赖顺序、并行机会、风险等级和预算约束”做调度。

**一句话版**

子任务分配的核心不是切得多细，而是通过模板化拆解、能力路由、依赖图、风险分级和动态重规划，把对的任务交给对的执行单元。

### 28. 如何确认这个子任务已经是最小的原子单元？有哪些具体措施？


**标准回答**

我理解这里的“原子单元”不是越小越好，而是细到可以被一个执行单元稳定完成、独立验证、独立重试和独立审计。再往下拆只会增加协调成本，而不再提升成功率。

要判断一个子任务是不是已经足够原子，我通常会做这些检查。

第一，做单一目标检查。一个原子任务通常只对应一个核心动作词，比如“拉取”“检索”“汇总”“验证”“生成”。如果任务描述里同时出现“并且”“然后”“同时”，通常说明它还包含多个目标。

第二，做单责任主体检查。一个原子任务应该能明确交给一个 Agent、一个工具链或一个执行器完成。如果必须两个角色反复来回配合才能结束，通常说明边界还没切干净。

第三，做输入输出清晰性检查。一个原子任务必须明确：

- 输入是什么
- 输出是什么
- 用什么格式交付
- 完成标准是什么

如果这些还说不清，那它大概率还不是可执行的原子任务。

第四，做完成定义（DoD）检查。也就是为每个子任务写清楚 done criteria。比如“拿到昨天支付接口的错误率和 P95 延迟曲线”是可验收的；“研究一下支付问题”就不是。

第五，做可独立验证检查。执行完后，系统应该能立刻判断成功、失败或证据不足。如果一个子任务做完后还无法判断是否完成，说明它通常还太大或太抽象。

第六，做可独立重试检查。一个原子任务失败后，应该可以只重试这一小步，而不需要把整个大任务推倒重来。如果不能独立重试，边界通常还不合理。

第七，做幂等性检查。尤其是有工具调用或状态写入的任务，要确认重复执行是否可接受，或者是否有幂等键和去重策略。不能重放的任务通常要进一步拆开，把“判断”和“执行”分离。

第八，做副作用隔离。像“改配置”“发邮件”“执行 SQL”“调用写接口”这类有副作用的动作，最好单独成任务，不要和“分析”“判断”“总结”混在一起。

第九，做复杂度阈值控制。如果一个子任务同时依赖多个数据源、多个判断条件、多个输出项，或者执行过程中要调用很多工具，它通常就还不是最小合理原子单元。

第十，做时长阈值控制。如果某个子任务经常执行很久、阻塞后续流程或者需要很多轮交互，工程上我一般会设置阈值，超过阈值就强制回到 planner 做二次拆分。

第十一，做拆解校验器。也就是在 planner 输出后加一层 rule check，比如检查：

- 是否有多个目标
- 是否有多个 owner
- 是否缺少 done criteria
- 是否未声明依赖
- 是否同时包含分析和执行

如果命中这些规则，就打回重拆。

第十二，做“继续拆分收益”判断。如果继续拆只会把一个自然完整动作拆成机械碎片，导致消息更多、状态同步更复杂、调度成本更高，那通常说明它已经足够原子了。

所以我通常用一句话判断：如果一个子任务已经能在清晰输入约束下，被单个执行单元完成，并且结果可验证、可重试、可审计，那它通常就已经是合适的原子单元。

**一句话版**

判断是否已经原子化，不是看拆得够不够碎，而是看它是否满足单一目标、单一责任、输入输出清晰、可独立验证、可独立重试和副作用隔离。

## 五、MCP、Skill 与 Agent 产品形态

### 29. MCP 是什么？有哪些分类？MCP Server 怎么开发？Transport 有哪些？为什么重要？


**标准回答**

MCP，Model Context Protocol，可以理解成 AI 应用与外部工具、数据源、工作流之间的统一协议标准。它解决的是工具接入不统一、每个 Agent 产品都要单独适配的问题。

从角色上看，MCP 一般分为：

- `Host`：承载 AI 应用的宿主，即用户直接交互的 AI 应用本身（如 Claude Desktop、Claude Code、Cursor）。Host 负责管理用户界面和对话流程，内部创建并管理一个或多个 Client 实例，控制安全策略——决定 Server 暴露的能力中哪些可以交给 LLM 使用，协调 LLM 与外部能力的交互（用户确认、权限审批等）。
- `Client`：代表宿主去连接 Server 的协议客户端。每个 Client 实例与一个 Server 保持 1:1 的有状态会话。Client 负责发起连接（协议握手、能力协商）、将 Host 的请求翻译为 MCP 协议消息发送给 Server、接收 Server 的响应并转发回 Host、维护会话状态（连接生命周期、心跳、重连等）。Client 对 Host 来说是透明的中间层，Host 不需要关心底层传输细节。
- `Server`：暴露工具、资源、提示模板等能力的服务端。Server 暴露三类能力：Tools（可执行的操作，如查数据库、调 API、读文件）、Resources（可读取的数据源，如文件内容、数据库表）、Prompts（预定义的交互模板，如代码审查模板、翻译模板）。

三者的连接流程如下：

```
┌─────────────────────────────────────────────┐
│                  Host                        │
│  (Claude Desktop / Claude Code / 你的应用)     │
│                                              │
│   ┌──────────┐  ┌──────────┐  ┌──────────┐  │
│   │ Client A │  │ Client B │  │ Client C │  │
│   └────┬─────┘  └────┬─────┘  └────┬─────┘  │
└────────┼──────────────┼──────────────┼───────┘
         │              │              │
    MCP 协议         MCP 协议       MCP 协议
    (stdio)         (stdio)     (SSE/HTTP)
         │              │              │
   ┌─────┴─────┐  ┌─────┴─────┐  ┌────┴──────┐
   │ Server A  │  │ Server B  │  │ Server C  │
   │ (文件系统) │  │ (数据库)   │  │ (远程API) │
   └───────────┘  └───────────┘  └───────────┘
```

连接建立过程：Host 启动时读取配置，得知需要连接哪些 Server；Host 为每个 Server 创建一个 Client（严格 1:1）；Client 发起连接，本地场景使用 stdio（Client 作为父进程启动 Server 子进程，通过标准输入/输出通信），远程场景使用 SSE + HTTP；连接建立后进行能力协商（Initialize），Client 和 Server 交换协议版本和能力清单；Host 拿到所有 Server 暴露的 tools/resources/prompts 后注入 LLM 上下文。

一次典型调用：用户提问 → Host 将问题发给 LLM → LLM 决定调用某个 tool → Host 找到该 tool 所属的 Client → Client 将请求通过 MCP 协议发给对应 Server → Server 执行操作返回结果 → Client 将结果转回 Host → Host 将结果交给 LLM 继续推理 → LLM 生成最终回复。

关键设计点：Client 与 Server 1:1，一个 Server 崩溃不影响其他 Server；Host 掌控安全边界，Server 暴露了工具不代表 LLM 能直接调用，Host 可要求用户确认或直接屏蔽；Server 彼此隔离，避免横向安全风险。

从部署形态看，可以分为：

- 本地 MCP Server，比如基于 `STDIO`
- 远程 MCP Server，比如基于 `HTTP / Streamable HTTP`

从能力语义看，常见是：

- `Tools`
- `Resources`
- `Prompts`

开发 MCP Server，一般分三步：

1. 先定义能力边界，明确要暴露哪些工具或资源、参数和权限范围。
2. 用官方 SDK 实现协议层。
3. 选择 transport，比如本地用 `STDIO`，远程服务用 `Streamable HTTP`。

Transport 常见类型：

- `STDIO`：适合本地工具和桌面端集成
- `Streamable HTTP`：更适合生产环境
- `SSE`：早期常见，但现在更多是兼容方案

MCP 在 Agent 生态里重要，是因为它把能力接入标准化了，让工具提供方和 Agent 产品之间不再是大量点对点耦合。

**一句话版**

MCP 的核心价值不是多一个协议名词，而是把 Agent 的工具接入层标准化，降低生态集成成本。

### 30. Agent 架构中的 Skill 有什么特点和优势？


**标准回答**

Skill 是 Agent 能力的最小可复用单元，每个 Skill 封装一个完整的、边界清晰的能力。它有四个核心特点：

第一，原子化封装。每个 Skill 有明确的输入/输出契约（参数 schema + 返回格式），内部逻辑对外不可见，调用方只关心"能做什么"，不关心"怎么做"。粒度介于底层函数和完整工作流之间。

第二，声明式注册，运行时发现。Skill 不是硬编码在 Agent 代码中的，而是通过声明式元数据注册（名称、描述、参数 schema、前置条件等），Agent/LLM 在运行时根据任务需求动态发现和选择。传统方式是 `if task == "翻译": call translate()` 硬编码分发；Skill 方式是 LLM 读取所有 Skill 描述后自主决定调用哪个，实现动态匹配。

第三，可组合性。Skill 之间可以自由组合形成更复杂的工作流，Agent 不需要预定义组合方式，LLM 根据任务目标自主决定调用顺序和组合策略。

第四，热插拔，零耦合。新增 Skill 不需要修改 Agent 核心代码，注册即可用；移除 Skill 不会影响其他 Skill 的运行；升级 Skill 的内部实现，只要接口不变，调用方无感知。

Skill 的核心优势包括：能力复用（同一个 Skill 可被多个 Agent、多个工作流复用）、降低 Agent 复杂度（Agent 只负责推理和编排，具体执行委托给 Skill）、生态扩展性（第三方可独立开发 Skill 并接入）、易于测试（每个 Skill 可独立单测）、权限可控（在 Skill 粒度上做权限管理）、渐进增强（新增一个 Skill 就多一项能力）。

和直接 Tool 调用相比，Skill 本质上是在 Tool 的基础上加了一层语义抽象——让 Agent 不仅能"调用工具"，还能"理解这个工具是什么、适合什么场景、需要什么前提条件"，从而实现更智能的自主编排。

**一句话版**

Skill 是 Agent 的原子化可复用能力单元，通过声明式注册 + 运行时发现 + 热插拔机制，让 Agent 能力可组合、可扩展、可治理。

#### 补充：MCP 和 Skill 的区别是什么？

这两个概念经常一起出现，但它们不在同一层。

- `MCP` 更偏“协议和接入标准”
- `Skill` 更偏“能力封装和运行时调用单元”

可以直接这样对比：

| 维度 | MCP | Skill |
|---|---|---|
| 本质 | 一种标准化协议 | 一种能力封装单元 |
| 关注点 | 怎么把外部工具、资源、Prompt 标准化接进来 | 怎么把某项能力封装成 Agent 可调用的原子单元 |
| 所在层级 | 更偏基础设施层、集成层 | 更偏能力层、编排层 |
| 面向对象 | Host / Client / Server 之间的连接与通信 | Agent / Orchestrator 对能力的选择、调用和组合 |
| 解决的问题 | 工具接入不统一、生态适配成本高 | 能力难复用、难治理、难组合 |
| 典型内容 | Tools、Resources、Prompts、Transport、协议握手 | 名称、描述、输入输出 schema、前置条件、返回结果 |
| 运行形态 | 常常是一个独立 Server，通过协议暴露能力 | 常常是平台内部注册的一项能力，也可以底层再调用 Tool 或 MCP Server |
| 粒度 | 更像“连接器 / 接口规范” | 更像“可执行能力块” |
| 是否强调协议兼容 | 强调 | 一般不强调 |
| 是否强调语义抽象 | 相对弱，重点是标准化暴露能力 | 更强，重点是让 Agent 理解“这个能力适合做什么” |
| 和 Agent 的关系 | 给 Agent 提供统一工具接入方式 | 给 Agent 提供可选择、可组合的执行能力 |
| 一个直观类比 | 像 USB / HTTP 这种“接入标准” | 像“翻译”“查日志”“生成报告”这种具体技能 |

它们的关系通常是：

- `MCP` 负责把能力接进来
- `Skill` 负责把能力组织成 Agent 易于理解和调用的语义单元

所以实际系统里经常会出现这种分层：

1. 底层通过 `MCP Server` 接入文件系统、数据库、搜索、浏览器等外部能力。
2. 中间层把这些 Tool/Resource 进一步封装成 `Skill`，比如“网页调研”“报表生成”“日志排障”。
3. 上层 Agent 再根据任务目标去选择和编排这些 Skill。

如果用一句更面试化的话来说：

- `MCP` 解决“能力怎么标准化接进来”
- `Skill` 解决“接进来的能力怎么被 Agent 更好地理解、复用和编排”

**面试表达**

MCP 和 Skill 不在同一个抽象层。MCP 是工具和数据源接入的协议标准，解决的是生态集成和互操作问题；Skill 是能力封装单元，解决的是 Agent 内部的能力复用、语义抽象和运行时编排问题。可以把 MCP 理解成“标准化插座”，把 Skill 理解成“插上去以后可直接使用的功能模块”。实际架构里常常是 MCP 负责接入，Skill 负责封装，Agent 负责决策和编排。

### 31. 能在 Skill 上编排 Agent 吗？Skill 和 Sub-Agent 的关系是什么？


**标准回答**

可以，但要分清方向和约束。

主流做法是 Agent 编排 Skill：Agent 是大脑，Skill 是手脚，Agent 根据任务目标自主决定调用哪些 Skill、以什么顺序组合。

但反过来也可以——一个复杂 Skill 内部可以启动 Sub-Agent 来完成工作。典型场景包括：需要多视角分析（研究类 Skill 内启动多个 Agent 分别从不同角度分析）、需要迭代推理（代码生成 Skill 内启动一个 Agent 做"写代码→跑测试→修 bug"循环）、需要并行执行（数据处理 Skill 内启动多个 Agent 并行处理不同数据分片）。

但这种做法有四个关键约束：

第一，Skill 对外仍然是原子的。无论内部启了多少 Sub-Agent，对调用方来说 Skill 还是一个黑盒——输入参数、输出结果、完成或失败，没有中间态暴露。

第二，控制层级要清晰，避免递归失控。建议嵌套不超过 2 层：主 Agent → Skill → Sub-Agent（到此为止，Sub-Agent 只调用 Tool/函数），否则调试、超时控制、错误传播都会变得极其复杂。

第三，资源和上下文隔离。Sub-Agent 不应该共享主 Agent 的完整上下文，原因包括：安全上 Sub-Agent 只需知道完成子任务所需的最小信息；成本上传递完整上下文浪费 token；可靠性上隔离后单个 Sub-Agent 失败不会污染主 Agent 状态。

第四，超时和成本需要 Skill 层兜底。Skill 层负责超时熔断、预算控制、结果聚合、异常兜底。

**一句话版**

Skill 内部可以编排 Sub-Agent，但要保持对外原子性、层级不超过 2 层、上下文隔离、资源有兜底，核心原则是 Skill 对外是黑盒，对内自由编排。

### 32. 怎么理解 Claude Code、Codex、Manus 这类 Agent 产品？


**标准回答**

我会把这类产品看成面向具体工作域的 agentic product，而不是传统聊天机器人。

它们和传统 chat agent 的区别主要在四点：

- 面向目标，而不是只面向问句
- 具备计划和分解能力
- 有真实执行面，比如文件系统、shell、浏览器、代码仓库
- 有验证闭环，比如测试、编译、回滚、重试

它们的底层架构逻辑通常很接近：

- `Planner`：拆任务和决定下一步
- `Context Builder`：组装代码库、文档和历史上下文
- `Tool Layer`：文件编辑、命令执行、浏览器、搜索、Git
- `Execution Sandbox`：隔离执行环境
- `Memory / State`：记录过程状态
- `Verifier`：测试、lint、结果校验
- `Human Checkpoint`：关键动作前确认

所以这类产品的工程能力并不是模型“自己突然学会工程了”，而是靠工具链、执行环境、状态管理和验证闭环共同补出来的。

**一句话版**

Claude Code、Codex、Manus 的核心价值不在“更会聊天”，而在“能不能把任务做完并交付结果”。

### 33. Deep Research 类 Agent 要配备哪些工具？基础设施和安全挑战是什么？


**标准回答**

Deep Research 不是给模型加个搜索框，而是一个多阶段的信息搜集、验证、综合和产出系统。

工具层至少需要四类能力：

- 信息获取：Web 搜索、网页抓取、PDF 解析、数据库和内部知识库连接器
- 信息处理：摘要、去重、表格抽取、实体抽取、对比分析
- 信息验证：来源可信度评估、交叉引用、时效性检查、数值一致性校验
- 信息产出：结构化报告、表格、图表、文档生成

基础设施上，常见拆法是：

- `Planner Agent`：拆问题和规划子任务
- `Researcher Agents`：并行搜索不同来源
- `Verifier / Critic Agent`：核对引用、冲突和时效
- `Writer Agent`：汇总成最终报告
- `Orchestrator`：管理状态、预算和终止条件

底层还需要任务队列、并发调度、统一检索层、文档解析服务、结果缓存、citation store、长任务状态存储、token 预算控制和 trace/replay。

安全和基建挑战主要是：

- 来源污染和 prompt injection
- 引用不可信或结论与证据脱节
- 长任务导致 token、时延和成本很高
- 企业连接器权限边界复杂
- 结果需要可追溯、可审计、可回放

**一句话版**

Deep Research 的核心难点不在“搜得到”，而在“证据是否可信、过程是否可追溯、长任务是否可控”。

## 六、Agent 评估、幻觉与安全治理

### 34. Agent 评估体系包括哪些维度？如何衡量 planning 能力和 hallucination rate？


**标准回答**

Agent 的评估体系，我一般会分成五个维度：任务完成、过程质量、工具使用、事实可靠性、系统效率。

第一，任务完成维度。主要看最终有没有把事做完，比如任务成功率、子任务完成率、一次完成率、人工接管率、失败回滚率。这一层最关注结果。

第二，过程质量维度。主要看 Agent 的执行过程是不是合理，核心包括 planning 能力、步骤完整性、是否走弯路、是否重复调用、是否能根据中间结果动态调整计划。这一层评估的是“怎么做事”。

第三，工具使用维度。主要看工具选得对不对、参数传得对不对、调用是不是必要、失败后会不会切换路径。常见指标包括工具调用成功率、无效调用率、关键工具命中率、平均工具调用次数。

第四，事实可靠性维度。主要看 hallucination，也就是是否编造事实、错误引用、证据和结论不一致。常见指标包括事实错误率、证据支撑率、引用正确率、无依据断言占比、拒答准确率。

第五，系统效率维度。包括响应时延、token 消耗、工具调用成本、长任务平均完成时间、单位成功任务成本。企业场景里这层很重要，因为 Agent 不只是要会做，还要做得划算。

如果单独讲 planning 能力和 hallucination rate，我会把它们分开评估。

先说 planning 能力。planning 不是看“计划写得像不像”，而是看这个计划是否真的帮助任务更稳定完成。常见评估方式包括：

- 计划完整性：关键步骤是否覆盖
- 计划正确率：顺序是否合理，是否漏掉关键动作
- 动态调整能力：中间结果变化后，能不能修正计划
- 冗余度：有没有重复步骤、无意义循环
- 计划执行一致性：前面说的计划和后面实际执行是否一致
- plan-to-success 相关性：计划质量提升后，任务成功率是否显著改善

如果是离线评估，一般会准备任务集和参考解法，看 Agent 的计划是否覆盖关键节点；如果是在线评估，会更关注任务成功率、平均步数、重复动作率、人工干预率这些行为指标。

再说 hallucination rate。它重点不是看回答流不流畅，而是看“说的内容有没有证据支持”。常见量化方式包括：

- 事实错误率：输出里有多少事实是错的
- 无依据断言占比：结论是否在上下文或工具结果里找不到支撑
- 引用正确率：引用的文档、日志、结果是否真实对应
- 证据一致性：结论是否和 retrieval 结果、tool output 一致
- 拒答准确率：证据不足时能不能克制，而不是硬编

在 Agent 场景里，hallucination 不只是文本编造，还包括动作幻觉，比如编造工具执行结果、编造文件已修改、编造某个 API 已调用成功、编造某条日志或监控结论。所以评估时最好把文本幻觉和动作幻觉分开看。

这两个指标虽然都影响任务质量，但本质不同。planning 评估的是决策过程是不是合理，hallucination 评估的是事实和证据是不是可靠。一个 Agent 可能 planning 很强，但中间引用了错误事实；也可能几乎不幻觉，但规划能力很弱，做事没章法。所以这两个维度不能混成一个总分。

**一句话版**

Agent 评估体系我通常分成任务完成、过程质量、工具使用、事实可靠性和系统效率五层。planning 能力主要看任务拆解是否完整、顺序是否合理、是否能根据反馈动态调整；hallucination rate 主要看输出和动作是否有证据支撑、是否存在无依据断言或编造工具结果。前者评估“怎么做事”，后者评估“说的是不是真的”。

#### 补充：Faithfulness 和 Answer Relevance 是什么？

这两个概念通常出现在 RAG 或 LLM 回答质量评估里，但关注点不一样。

`Faithfulness` 一般翻成忠实性或事实一致性。它关注的是：模型的回答是否忠实于给定证据，有没有脱离上下文乱编。也就是说，判断重点是回答和检索证据、工具结果、引用内容是否一致。

你可以把它理解成：

- 关注“有没有编”
- 看回答和证据是否一致
- 核心是控制 hallucination

例如，给定证据只说明“接口超时和数据库连接池耗尽有关”，但模型回答成“已经确认是 Redis 故障”，那这条回答的 faithfulness 就很低，因为它不忠于证据。

`Answer Relevance` 一般翻成回答相关性。它关注的是：模型的回答有没有真正回应用户的问题，是不是切题。也就是说，回答可能没有乱编，但如果答偏了、答泛了、没有抓住用户真正的问题，那 relevance 还是会低。

你可以把它理解成：

- 关注“有没有答到点上”
- 看回答和问题是否匹配
- 核心是防止答非所问

例如，用户问“为什么支付接口超时”，模型回答“数据库连接池是系统中的重要组件，通常用于管理连接资源”，这段话可能没有编造，也和主题相关，但没有直接回答“为什么超时”，所以 answer relevance 不高。

一句话区分就是：

- `Faithfulness`：回答是否忠于证据
- `Answer Relevance`：回答是否切中问题

**面试表达**

Faithfulness 主要评估回答和检索证据是否一致，防止模型脱离上下文产生幻觉；Answer Relevance 主要评估回答是否真正回应了用户问题，防止答非所问。前者关注“有没有编”，后者关注“有没有答对题”。

### 35. 当大模型产生错误回答或幻觉时，在工程和算法层面有哪些规避手段？


**标准回答**

如果大模型出现错误回答或幻觉，我一般会从工程层和算法层同时处理。因为工程层解决的是“即使答错也别出事故”，算法层解决的是“尽量少答错”。

先说工程层面的规避手段。

第一，限制模型职责边界。不要让模型直接做最终裁决者，尤其是在高风险场景里。更合理的方式是让模型负责分析、归纳、生成候选方案，而把执行和最终判断交给规则系统、校验器或人工审批。

第二，要求回答必须基于证据。在 RAG 或工具调用场景里，要求模型回答时引用检索证据、日志、数据库结果或工具输出。没有证据支撑时，要允许模型明确说“不确定”或“信息不足”。

第三，做结果校验。模型输出后不直接信任，而是增加校验层，比如规则校验、格式校验、事实一致性校验、工具结果比对、敏感词检测和风险动作检测。

第四，动作分级和审批。只读动作可以自动执行，中风险动作需要确认，高风险动作必须人工审批。这样即使模型幻觉，也不至于直接变成生产事故。

第五，做拒答和降级。当检索结果质量差、证据冲突、置信度过低时，系统不要硬答，可以选择拒答、返回相关文档、引导补充信息或者转人工。

第六，建立反馈闭环。把错误回答和幻觉案例沉淀成评测集，持续回归测试，并根据错误类型优化检索、提示词、工具链和校验器。

再说算法层面的规避手段。

第一，优化 RAG 和检索质量。很多幻觉本质上是“没有拿到正确证据”，所以要提升召回和排序质量，比如优化 chunk 切分、混合检索、rerank、metadata 过滤和 query rewrite。

第二，强化 grounded generation。也就是让模型尽量基于外部证据回答，而不是只靠参数记忆。常见做法包括明确要求只能依据给定上下文回答、没有证据时必须拒答、输出时附带引用。

第三，优化 prompt 约束。比如明确告诉模型不要编造、不确定就说不知道、先给结论再给证据、只能使用提供的数据源。它不能彻底解决幻觉，但可以降低出错概率。

第四，采用多阶段生成。不要一步到位直接生成最终答案，而是拆成检索证据、判断证据是否充分、生成候选答案、再做自检或验证几个阶段。

第五，引入 verifier 或 critic 机制。可以让另一个模型，或者同一个模型的第二轮，对结果做事实核对、引用核对和一致性检查，用于发现明显幻觉。

第六，在固定业务域里做领域优化。如果场景比较垂直，比如金融、医疗、运维，可以通过领域数据微调、偏好优化和拒答样本训练，减少不靠谱输出。

**一句话版**

处理大模型幻觉，我一般分工程层和算法层。工程层重点是把风险关住，包括证据约束、结果校验、动作分级、审批、拒答和反馈闭环，保证模型即使答错也不会直接造成事故；算法层重点是降低幻觉发生率，包括优化 RAG 检索、增强 grounded generation、加强 prompt 约束、多阶段生成和 verifier 校验。核心目标不是假设模型永远正确，而是让它尽量少错、错了也可控。

### 36. 如何维护 Agent 生成的证据链？怎么尽量避免幻觉？


**标准回答**

我理解的证据链，不是把模型所有内部思维过程暴露出来，而是把“结论基于什么信息得出”这件事做成可追踪、可核验、可审计的链路。

如果让我做，我会把四类东西明确分开：

- `observation`：原始观测，比如日志、网页、数据库结果、工具输出
- `evidence`：被选中用于支撑结论的关键证据
- `inference`：基于证据做出的推断
- `decision`：最终建议、答案或执行动作

这四层不要混写。尤其不能让模型把“推断”包装成“观测事实”。

维护证据链时，我通常会做这些事。

第一，原始结果单独落盘保存。比如工具结果、检索片段、日志片段、网页引用都要有 `source_id` 或 `evidence_id`，不能只留下模型总结。

第二，结论必须引用证据。无论是答案还是执行建议，都应该能回溯到一个或多个 `evidence_refs`。如果没有证据支撑，那它只能叫“假设”，不能叫“结论”。

第三，做证据和结论的一致性校验。至少要检查三件事：

- 引用的证据是不是真存在
- 结论是否被证据支持
- 多个证据之间是否冲突、是否过期、是否越权

第四，把“事实判断”和“动作执行”拆开。先判断，再验证，再执行。不要让一个未校验的自然语言结论直接进入有副作用的动作层。

第五，给系统设计拒答和降级能力。如果证据不足、来源冲突或时效不明，系统应该明确说“不确定”或“需要更多验证”，而不是为了流畅强行补全。

第六，加入 verifier 或规则校验器。尤其在高风险任务里，不能只相信生成模型自检。可以用规则、第二模型或外部程序对引用、时间、实体、数值和逻辑一致性做二次校验。

为什么这样能降低幻觉？因为很多幻觉本质上来自三件事：

- 把记忆当事实
- 把推断当证据
- 把语言流畅性当正确性

证据链的作用，就是把这三件事拆开，让模型就算想“编”，也更容易被发现和阻断。

当然，证据链也不是万能的。它更适合控制“是否有依据”“依据是否一致”，但不能天然保证依据本身一定真实。所以还要配合来源可信度评估、时间校验、权限过滤和人工抽检。

**一句话版**

维护证据链的关键不是暴露全部思维，而是把观测、证据、推断、决策分层，并让每个结论都能追溯到具体依据。

### 37. 你觉得目前模型或 Agent 存在什么安全问题？比如 prompt 注入、投毒、模型窃取等


**标准回答**

我一般会把模型和 Agent 的安全问题分成六大类来看，而且 Agent 的风险通常比纯问答模型更高，因为它不只是“会说”，还可能“会做”。

第一类是 `prompt injection / jailbreak`。攻击者通过用户输入、网页内容、PDF、邮件、知识库文档或工具返回结果，把恶意指令混进上下文，诱导模型忽略系统规则、泄露内部信息或调用不该调用的工具。

第二类是数据投毒。包括训练数据投毒、知识库投毒、网页投毒、memory 污染和反馈回路污染。它的风险在于系统可能长期学习到错误模式，而不是单次回答出错。

第三类是工具滥用和越权执行。Agent 有工具调用能力后，风险就从“回答错”升级成“操作错”。比如本不该访问的数据被检索出来，本不该执行的写动作被执行。

第四类是敏感信息泄露。包括系统 prompt 泄露、跨租户数据串扰、RAG 检索把越权数据带进上下文、日志里记录了敏感参数、工具结果中包含敏感字段等。

第五类是模型窃取和 Prompt 窃取。比如通过 API 高强度查询做模型抽取、蒸馏近似，或者想办法诱导系统吐出内部 prompt、策略规则、工具描述和安全边界。

第六类是资源滥用，也可以理解成 `denial of wallet`。攻击者不一定要把系统打挂，只要让 Agent 进入超长上下文、反复调用工具、循环重试，就可能把 token 成本和外部调用成本迅速拉高。

如果从工程角度讲，我最关注的是四个高风险组合：

- prompt 注入 + 工具调用
- 检索投毒 + 证据污染
- memory 污染 + 长期行为偏移
- 越权检索 + 自动执行

因为这些组合会把模型的不确定性直接传导到生产动作。

防御上我一般不相信单点方案，而是做分层治理：

- 权限隔离：工具和数据都按用户、租户、scope 控制
- 上下文分层：系统指令、工具结果、外部内容不能混成一层
- 结构化调用：工具必须走 schema 和白名单
- 风险分级：高风险动作强制审批或人工确认
- 观测审计：记录 trace、tool call、retrieval、memory 命中和最终动作
- 输出校验：对关键结论和动作做 verifier 或规则检查

**一句话版**

模型安全的核心风险是“被误导”，Agent 安全的核心风险是“被误导以后还能执行动作”，所以 Agent 的防护一定要比普通聊天系统更强。

### 38. Prompt 注入一般是怎么发生的？怎么防御？


**标准回答**

从安全视角看，prompt 注入的本质是：把“不可信输入”伪装成“高优先级指令”，让模型错误地服从它。

常见路径主要有三类。

第一类是直接注入，也就是恶意内容直接出现在用户输入里。比如用户试图让模型忽略既定规则、泄露系统信息、绕过原本的回答边界。

第二类是间接注入，也就是恶意内容藏在网页、PDF、邮件、工单、知识库文档、代码注释等外部材料里。Agent 去读这些材料时，把其中的恶意指令也一并当成上下文带了进来。

第三类是工具结果注入。比如搜索结果、OCR 结果、数据库文本字段、第三方接口返回值里带有操纵性文本。因为这些内容看起来像“系统拿到的事实”，所以更容易被误信。

真正危险的地方在于，prompt 注入往往不是单独存在，而是和工具调用、检索、memory 写入一起连锁发生。一旦进入链路，它可能从一次错误回答，升级成错误检索、错误记录甚至错误执行。

防御上，我一般会强调一句话：prompt 注入不能只靠 prompt 防，它本质上是一个权限和信任边界问题。

具体会做这几层防护。

第一，做信任分层。系统指令、开发者规则、工具协议、外部文档、用户输入要分层处理。外部内容永远只当“数据”，不能自动升级成“指令”。

第二，做工具白名单和 schema 校验。模型不能自由拼接任意命令，所有工具调用都应该是结构化参数、受限动作和显式权限校验。

第三，做检索前后的过滤。检索前控制权限范围，检索后对结果做 `sanitize`、去噪、来源标记和敏感字段处理，防止把污染内容原样塞进核心 prompt。

第四，做动作分级。只读动作可以相对自动化，低风险写动作要求确认，高风险动作必须人工审批或双重确认。

第五，做 memory 写入 gating。不要把每次对话和外部内容都直接写进长期记忆，否则一次注入可能变成长期污染。

第六，做结果校验和审计。对关键结论、关键工具调用和最终动作增加 verifier、规则校验器和全链路审计，保证事后能追溯、事中能阻断。

如果面试官追问“那是不是能彻底防住”，我一般会回答：很难做到绝对防住，但可以通过权限隔离、结构化工具调用、上下文分层和人工审批，把风险从“直接执行”降到“可发现、可阻断、可追溯”。

**一句话版**

Prompt 注入本质上不是一句恶意提示词的问题，而是系统把不可信内容和高权限指令混在一起了。防御关键在信任分层、权限控制、结构化工具调用和高风险动作审批。


### 39. Mock 是怎么实现的？

**标准回答**

Mock 的本质是：在测试运行时，用一个“可控替身”替换真实依赖，让我们只测试当前模块的逻辑，而不依赖真实数据库、网络、缓存、时间或第三方服务。

如果从实现机制上看，Mock 一般有四步。

第一，找到依赖边界。通常适合被 mock 的对象包括：

- HTTP 请求
- 数据库访问
- Redis / 缓存
- 文件系统
- 时间和随机数
- 第三方 API
- LLM 调用
- Tool 调用

第二，把真实依赖替换成测试替身。也就是在测试里把原来代码会调用到的对象，换成一个假的对象或假的函数。这样业务代码本身不用改，但执行时访问到的是我们预先注入的替身。

第三，预设替身行为。也就是提前告诉这个 mock：

- 应该返回什么值
- 什么时候抛异常
- 是否按顺序返回不同结果
- 是否记录调用参数和调用次数

这样就能模拟成功、失败、超时、重试、限流、空结果这些场景。

第四，校验交互。测试不只看最终结果，还要看：

- 有没有被调用
- 调用了几次
- 参数是否正确
- 调用顺序是否符合预期

如果再往底层解释，Mock 之所以能工作，本质上是“运行时替换引用”。代码以为自己调用的是真实对象，但测试环境把那个引用指向了一个可控替身，所以后续行为全在测试控制里。

以 Python 为例，常见实现方式有三类。

第一类是 `unittest.mock.patch`。它会把某个函数、方法、类或模块引用在运行时临时替换成 `Mock` 对象。比如你 patch 了 `module.client.send`，那测试执行期间，这个调用就不会走真实发送逻辑。

第二类是 `pytest` 的 `monkeypatch`。它适合直接改模块属性、环境变量、全局对象或方法引用，本质上也是替换运行时依赖。

第三类是依赖注入。也就是在设计代码时，不直接在函数内部 new 出真实依赖，而是把依赖作为参数传进去。测试时传 fake/mock，实现时传真实对象。这种方式通常更稳定，也更容易测试。

在工程里，我一般不会只用一种 mock 方式，而是分层使用。

- 单元测试里，多用函数级 mock 或 repository mock
- HTTP 测试里，用请求拦截或 transport mock
- 时间相关测试里，冻结时间或 patch 时间函数
- Agent / LLM 测试里，mock 模型返回、tool output、retrieval 结果，保证可复现

我还会特别强调一个常见坑：patch 要 patch “被当前代码引用的地方”，而不是“它最初定义的地方”。因为 Python 模块 import 后，实际调用的是当前命名空间里的引用。如果 patch 错位置，测试看起来写了 mock，实际还是在调用真实对象。

另外，Mock、Stub、Fake 这几个概念最好区分：

- `Mock`：更关注交互行为，比如有没有被正确调用
- `Stub`：更关注返回固定数据
- `Fake`：是一个可运行的简化实现，比如内存版数据库

如果是面试，我通常会补一句：单元测试里 mock 很有价值，但不能全靠 mock。因为 mock 太多容易把测试写成“验证 mock 本身”，而不是验证真实业务行为。所以集成测试里我更倾向 fake 或真实测试环境。

**一句话版**

Mock 的实现本质上就是在测试运行时，把真实依赖替换成可控替身，预设它的返回和异常，再校验当前模块和它的交互是否符合预期。

## 七、面试收口表达


如果面试官追问整体理解，可以用下面这段做总结：

> 我理解企业级 Agent 的关键，不是把大模型接进去，而是把规划、检索、记忆、工具、执行、安全和审计做成一个可控系统。Workflow 解决确定性流程，Agent 解决不确定性任务；RAG 解决知识可用性，memory 和 context 解决长任务连续性，MCP 解决工具接入标准化。真正的落地难点通常不在模型本身，而在权限边界、状态稳定、错误兜底和可观测性。
