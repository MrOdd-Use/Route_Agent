
系统介绍：
Route Agent 是一个给 AI Agent 智能分配大语言模型的路由系统。在多 Agent 应用里，不同 Agent 做的事差别很大——抓取网页、文本摘要、代码生成、分类翻译——如果全用贵的模型太浪费，全用便宜的又扛不住复杂任务。Route Agent 就是在质量和成本之间做自动调度。

系统分四个模块：

模型注册表负责管理可用模型。它对接了 OpenAI、DeepSeek、Google、Anthropic、Groq 五家云端供应商加本地 Ollama，通过 HTTP 拉取各家模型列表，统一标准化成包含定价、上下文窗口、能力评分的结构，以快照形式存到本地 SQLite，默认 30 天同步一次。路由时直接读本地数据，不用每次远程查。还可以接 Chatbot Arena 的榜单数据补充能力评分。

任务分析器是路由的输入端。走三层分析链路：先用本地 Ollama embedding 做向量画像匹配，把任务和已有 class pool 描述计算相似度；如果都低于阈值，再让大模型判断这个任务应该归入哪个已有类别，还是建议新增一个类池；如果前两层都失败，最后再退回到 legacy 关键词启发式兜底。这样既能让已知任务低成本、稳定命中，也保留了对新任务和新类别的扩展能力。

路由引擎是核心。它拿到分析结果和候选模型后做多层决策：先按能力维度匹配度和成本做综合打分排序；类别池里每个 model 都有历史表现记录，对于表现好或差的模型，对其进行增分和减分；同时检查模型健康状态和速率限制，不健康或快被限流的模型会被降权。引擎还有两个进阶机制：降级优化会在表现稳定时自动尝试用更便宜的模型替代，成功就永久切换，失败就回滚；升级逃逸则是在执行失败时沿候选列表向上尝试更强的模型。

监控模块旁路记录每次路由决策和执行结果，支持统计查询和实时观察，既用于排查问题，也为路由策略优化提供数据。

总的来说，系统先通过三层任务分析链路判断任务属于哪类、需要哪些能力，再从候选池中结合能力画像、历史战绩、实时状态和成本约束选出最优模型，并通过执行反馈持续学习，在不牺牲质量的前提下压低 Agent 的调用成本。



系统亮点介绍：

我觉得这个项目最大的技术亮点，同时也是最大的难点，是把“给不同 Agent 选合适模型”这件事，从经验判断做成了一套可学习、可解释、可观测的路由系统。这里面其实有1个核心难点：任务到底该匹配什么模型；

一开始我也考虑过做“成功案例库”这条路线。也就是当一个新任务进来时，先去找历史上相似的成功案例，再复用当时的模型选择。这种方法直观，但它有一个明显问题，就是容易形成路径依赖，对新模型不友好，系统会越来越偏向历史上已经用过的模型，缺少探索能力。后来结合这个项目的设计，我把它升级成了三层分析链路：先用向量画像去匹配任务和已有类池描述的相似度；如果匹配不够高，再用大模型判断这个任务是归入已有类别，还是应该建议新增一个类池；如果前两层都不稳定，再退回到 legacy 关键词启发式兜底。这样做的好处是，既能复用历史经验，又保留了对新任务和新类别的扩展能力。

在模型选择上，我没有把历史成功经验直接绑定到某一条具体 case，而是抽象成按任务类别维护的 class pool。也就是说，同一类 Agent 会沉淀出一组更适合它的模型池。真正路由时，也不是简单地选一个 top1，而是采用“保底强模型 + 类池优先 + 探索补位”的候选机制。池子数据少的时候，系统会增加探索比例，给新模型更多机会；池子足够成熟之后，就更多利用已经验证过的模型。再结合执行结果、质量反馈、模型健康状态和成本约束，持续更新类池，这样系统就能形成一个在线学习闭环。
