系统介绍：
Route Agent 是一个给 AI Agent 智能分配大语言模型的路由系统。在多 Agent 应用里，不同 Agent 做的事差别很大——抓取网页、文本摘要、代码生成、分类翻译——如果全用贵的模型太浪费，全用便宜的又扛不住复杂任务。Route Agent 就是在质量和成本之间做自动调度。

系统分五个模块：

模型注册表负责管理可用模型。它对接了 OpenAI、DeepSeek、Google、Anthropic、Groq 五家云端供应商加本地 Ollama，通过 HTTP 拉取各家模型列表，统一标准化成包含定价、上下文窗口、能力评分的结构，以快照形式存到本地 SQLite，默认 30 天同步一次。路由时直接读本地数据，不用每次远程查。还可以接 Chatbot Arena 的榜单数据补充能力评分。

任务分析器是路由的输入端。走三层分析链路：先用本地 Ollama embedding 做向量匹配，计算任务和已有类池描述之间的语义相似度——这里的类池是指每个任务类别对应的一组经过验证的候选模型；如果相似度都低于阈值，再让大模型判断这个任务应该归入哪个已有类别，还是建议新增一个类池；如果前两层都失败，最后退回到关键词启发式兜底。这样既能让已知任务低成本、稳定命中，也保留了对新任务和新类别的扩展能力。

路由引擎是核心决策层。它拿到分析结果和候选模型后做多层决策：先按能力维度匹配度和成本做综合打分排序；类池里每个模型的历史表现用置信下界来量化——样本越少分数越保守，只有积累了足够数据才会稳步提升，防止偶然好结果造成误判；同时检查模型健康状态和速率限制，不健康或快被限流的模型会被降权。候选集的构建采用"类池优先 + 强模型保底 + 留出探索空间"的策略——池子数据少时提高探索比例，给新模型更多进入机会；池子成熟后更多复用已验证的性价比模型。引擎还有两个进阶机制：降级优化会在表现稳定时自动用小流量试探更便宜的模型，成功就永久切换，失败就回滚；升级逃逸则是在执行失败时沿候选列表向上尝试更强的模型。

监控模块旁路记录每次路由决策和执行结果，支持统计查询和实时观察，既用于排查问题，也为路由策略优化提供数据反馈。

联邦模块是系统的第五层，解决的是跨应用经验共享的问题。单个应用本地路由能力完整，但新 Agent 或低流量任务类别样本少，冷启动慢。联邦层的做法是：各应用向中心注册自己的 Agent 列表，中心侧汇总不同应用在同类任务上的执行结果，同样用置信下界做跨应用聚合打分，再反哺到各本地路由——本地把自身经验和联邦经验按权重混合打分，低样本时更多依赖全局数据，本地数据充足后逐步回归自治。对于已注册的已知 Agent，客户端可以直接查本地缓存的类别映射，跳过三层分析链路，走轻量级分析直达路由引擎，大幅降低延迟。中心侧还会跟踪每个模型当前有多少应用在同时使用，一旦接近供应商的并发上限，就把后续流量重定向到其他候选模型，防止集中打爆限流。

总的来说，系统先通过三层任务分析链路判断任务属于哪类、需要哪些能力，再从候选池中结合置信打分、实时健康状态和成本约束选出最优模型，并通过执行反馈持续学习。联邦层让多个应用的路由经验可以互通共享，缓解冷启动和低样本问题。整套机制在不牺牲质量的前提下，持续压低 Agent 的调用成本。



系统亮点介绍：

我觉得这个项目最有价值、也最难的地方，是把“给不同 Agent 选合适模型”这件事，从过去靠人工经验做静态配置，做成了一套能持续学习、能解释决策、也能被观察和验证的自适应路由系统。这里真正的难点其实不只是“选哪个模型”，而是系统首先要判断当前任务到底属于什么类型、需要什么能力。因为前面这一步如果判断错了，后面的路由再精细也没有意义。

一开始我想过做“成功案例库”这条路线。也就是新任务来了，先去找历史上相似的成功案例，再复用当时效果最好的模型。这个思路很直观，但它的问题也比较明显，就是容易形成路径依赖，系统会越来越偏向已经用过的老模型，对新模型、新任务都不够友好，探索能力也会越来越弱。后来我把它升级成了三层分析链路：第一层先用向量画像去匹配任务和已有类池描述的相似度；如果匹配度不够高，第二层再交给大模型判断，这个任务是该归入已有类别，还是应该新建一个类池。这样做的好处是，既能复用历史经验，也不会把系统锁死在旧路径里，对新任务和新类别也有扩展空间。

在模型选择这一步，系统也不是每次都机械地选一个 top1，而是采用“保底强模型 + 类池优先 + 探索补位”的方式来生成候选。池子数据少的时候，会提高探索比例，给新模型更多进入机会；池子逐渐成熟之后，再更多复用那些已经验证过、性价比更高的模型。再结合执行结果、质量反馈、模型健康状态和成本约束，持续更新类池，最后形成一个可以在线迭代的学习闭环。
